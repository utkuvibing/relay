# P5.4 — Discussion CLI and durable escalation

Status: implemented; exit gate passed.

## Accepted scope

Expose the P5.3 runner through a CLI, persist actionable outcome observations,
and inspect discussion history after restart. New discussions use a dedicated,
workspace-linked Room and configured role bindings. No Task, Decision, approval,
or completion evidence is created. Semantic loop/convergence detection remains
deferred; this milestone does not close that broader P5 requirement.

## Commands and configuration

```text
relay discuss "topic" [--protocol PATH] [--json]
relay discuss --resume EXECUTION_ID [--json]
relay inspect-discussion EXECUTION_ID [--json]
relay status
```

- Resume rejects topic/protocol overrides. Resume and inspection accept exact IDs
  or unique literal prefixes; ambiguous IDs fail explicitly.
- Default protocol: packaged three-round debate, equivalent to the repository's
  `protocols/debate.yaml`. Custom YAML uses the existing strict loader.
- Participants resolve only through `roles:` configuration. Missing bindings are
  reported without selecting agents or editing configuration.
- The debate requires 22 turns. Existing defaults remain 16 turns and 3 blocking
  messages. Execution starts with the available allowance and stops at exhaustion;
  there is no automatic increase or full-schedule budget refusal.
- Exit codes: complete 0; refused/failed/escalated 1; invalid usage 2; pending
  delivery 3. Inspection returns 0 for valid stored records regardless of outcome.

Example configuration, assuming `gpt` already exists under `agents:`:

```yaml
roles:
  architect: gpt
  critic: gpt
  repository_expert: gpt
  moderator: gpt
communication:
  budgets:
    max_agent_turns: 22
    max_blocking_messages: 3
```

## Runtime and history

- `ProtocolRunner.prepare(spec)` validates and pins inputs without writes or
  provider calls. CLI creation commits Room and execution together, then resumes
  outside the transaction. Existing `start` and `resume` retain their signatures.
- `resume` records returned outcomes for persisted executions; `start` shares
  that path. Unknown executions and pre-execution refusals create no observation.
- Add `EventType.PROTOCOL_OUTCOME_RECORDED`, using the existing append-only event
  log and schema v7. `ProtocolOutcome` validates the versioned payload:
  `relay.protocol.outcome.v1`, execution identity, stop reason, available stage
  and occurrence, canonical output IDs, allowlisted refusal code, optional budget
  scope/dimension, and a ledger revision fingerprint.
- Outcomes carry no raw exception or provider error text. Human-action-needed
  reasons are budget exhaustion, policy refusal, request failure, and input
  refusal. Completion and pending delivery require no escalation.
- Unchanged observations are deduplicated against the execution's latest event
  inside `BEGIN IMMEDIATE`. A changed observation appends history. Observations
  never authorize delivery, increase budgets, or replace canonical ledger facts.
- Configuration drift guidance asks the user to restore pinned settings. Failed
  requests require a new execution. Changed pinned stage budgets require a new
  execution; aggregate allowances remain an explicit user configuration choice.

## Inspection and rendering

- A provider-free projection reads the saved definition, deterministic request
  IDs, validated stage facts, canonical outputs, and outcome history in one read
  snapshot. It never resumes, invokes providers, or materializes replies.
- The view shows identity, protocol, progress, canonical outputs/synthesis, last
  observation, escalation, and next action. Missing or stale observations are
  labeled; ledger progress and recorded outcome remain separate.
- `relay status` adds the five most recent discussions and inspection commands,
  preserving task reporting. Human output renders participant text literally.
- JSON uses `relay.discussion.v1`: execution/Room/Task identity, topic, protocol,
  progress, outputs, last observation, observation history, escalation, next
  action, and error. Pre-execution errors use the same envelope with null identity.
- Corrupt or unsupported records produce a safe inspection error. Interrupted
  executions remain discoverable and explicit resume performs recovery.

## Acceptance

explicit allowance increase and resume, outcome deduplication/history, custom
YAML removal, configuration drift, failed requests, pending exit status, safe
diagnostics, missing roles, usage errors, literal prefixes, literal rendering,
atomic creation, and unchanged canonical authority records.

Read-only inspection is checked with SQLite write authorization denied and after
reopening the database. Runner recovery checks inspect succeeded Runs whose
canonical replies were interrupted, then prove resume completes without another
provider turn. Packaged debate equivalence and wheel resource loading are checked.
