# P4.2 — Role/Logical-Agent Resolution + Relay-Mediated Delivery (config-backed resolver, strict run authorship, delivery binding into the crash-safe spine)

**Status:** FROZEN — rev 3. Rev 1's five grilled decisions and rev 2's blocker
fix + four hardening amendments stand; rev 3 (final freeze amendment,
2026-08-30) removes the `force=True` escape hatch entirely: **unconditional
at-most-once delivery initiation** per persisted Message — once
MESSAGE_DELIVERED is atomically committed with the recipient Run in Tx1, any
subsequent delivery attempt for that Message is a typed rejection with zero
store delta. Redelivery/retry semantics are deliberately NOT defined in P4.2
(P4.4/later work may add them explicitly). Supersedes rev 2 rows 14/17 (§8b).
Implementation may begin; the execution record (§9) is appended after merge.
When implementation begins, copy this document to
`docs/plans/p4.2-role-resolution-delivery-plan.md` (Plan-mode constraint kept
it out of the repo).
**Normative basis:** SPEC §8, §27 Phase 4, App. D.2/D.5/D.6/D.8/D.11-P4,
C.1/C.3/C.7-P4, A.2; P4.1 plan D3/D6 + rev-3 forward requirement (real Run
provenance for agent-authored messages).

## 0. Scope

**In:** additive `Message.run_id` + schema v4; strict authorship validation at the
bus boundary (bare logical-agent sender ⇔ run provenance); `roles:` config section
(role → configured agent name, AgentRole-valued keys, fully decoupled from
`reviewer:`); production `ConfigRoleResolver` (P4.1 D6 seam); `AgentFactory`
protocol + production factory helper (registry stays out of core);
`relay/core/delivery.py` — Relay-mediated delivery binding a persisted Message to
a concrete recipient Run through `run_ask` (family-blind, crash-safe spine);
**additive opt-in `run_ask` pre-provider seam** (companion event + veto, D14 —
the ONLY orchestrator change); `EventType.MESSAGE_DELIVERED` as a
binding-at-initiation marker persisted in Tx1; unconditional at-most-once
delivery initiation (typed rejection, zero store delta — no escape hatch);
deterministic delivery prompt
envelope with `context_refs` pass-through; additive `AgentRole.PARTICIPANT`;
structural + behavioral authority-boundary proofs extended to the delivery path.

**Out (explicit):** reply persistence and any reply-linkage representation
(P4.3 — user-frozen: delivery writes **zero** Message rows); bounded round-trips,
blocking waits, unresolved-blocking queries (P4.3/P6, Q-B); budgets/policy/
communication config (P5); multi-agent driver, loop control, delivery
retry/recovery, and no redelivery/retry semantics of any kind (P4.2 refuses all
re-initiation unconditionally; P4.4+ may add explicit mechanics —
`deliveries_for_message` read helper provided); D.10 context
reconstruction engine (references pass through `context_refs` raw — P4.2
implements no reconstruction; consumption is P4.4 driver policy / P7 engine);
CLI surfaces; seats/persistent Rooms (P7); TaskState/`run_build` changes
(`run_ask` changes are limited to the D14 seam; default behavior byte-identical).

## 1. Code audit — facts this builds on

* `ConversationBus` (`relay/core/bus.py`) is the single public write path for
  conversation traffic; `RoleResolver` is an injected Protocol (P4.1 D6);
  unresolved/ambiguous roles are rejected pre-persistence; broadcast, self-send,
  SYSTEM-reservation invariants (D13–D15) hold.
* `relay/core` must not import `relay.agents.registry` (AST-tested
  `TestConversationBusAuthorityBoundary` shape checks each module's own imports);
  `relay.core.orchestrator` already imports `relay.agents.base` + lazily
  `relay.harness.runtime` — the import pattern a delivery module may follow.
* Schema at `SCHEMA_VERSION 3`; migration discipline = ADD COLUMN only,
  `_MIGRATIONS` chain, fresh DBs traverse v1→v2→v3→v4 and converge; `messages`
  is append-only at both layers (`_APPEND_ONLY_TABLES` + `messages_no_update/_no_delete`
  triggers) — delivery therefore cannot mark messages "delivered"; the binding
  record must live in the event log.
* `run_ask` (`relay/core/orchestrator.py`) is the crash-safe, family-blind spine:
  **Tx 1** (BEGIN IMMEDIATE: `Run(RUNNING)` + `run_input` artifact +
  `AGENT_RUN_STARTED`) commits before provider I/O; final Tx records
  success/failure. Never raises for provider failures.
* `store.transaction()` = `BEGIN IMMEDIATE` — **nested transactions are
  impossible**, so a duplicate-delivery check and the marker insert can share one
  atomic boundary only INSIDE `run_ask`'s Tx1. This is what forces the D14 seam
  (a pre-Tx check in `MessageDelivery` would leave a check→insert race window).
* `_planner_for` precedent: harness profile downgrade to `READ_ONLY_ACCESS` via
  profile copy — BUT it falls back to `profile=None` (adapter default grant)
  when no profile exists. Delivery deliberately does NOT inherit that fallback
  (D8): always an explicit READ_ONLY instance.
* Harness grant translation is fail-closed pre-spawn per adapter (P2.4
  Antigravity precedent: unsupported grants refuse typed before spawn) — the
  mechanism D8's "unsupported READ_ONLY ⇒ typed refusal" rides on.
* Composition root is `relay/cli/main.py` (`build_agent` + `load_config`);
  `RelayConfig` has `agents:` map and a P3.3 `reviewer:` name ref — no `roles:`
  section yet.
* `build_room_feed` composes **all** EventLogEntry types generically (only
  MESSAGE_SENT markers are deduped) — a new EventType flows through with zero
  feed changes.
* `AgentRole` has no enum-equality/subset assertions in tests (unlike
  MessageType's subset assertions) — additive member is safe.
* Suite baseline after P4.1 rev 3: **489 passed / 9 skipped**, ruff clean.

## 2. Frozen decisions

| # | Decision |
|---|---|
| D1 | **Strict authorship (user-frozen, rev 1):** a bare logical-agent `sender` MUST carry `run_id`; the bus loads the Run and rejects (typed, pre-persistence) when the run does not exist or `run.agent != sender`. Symmetric rule: `human:*`/`relay:*` senders MUST NOT carry `run_id` (authorship proof is agent-only; prefix senders cite runs via generic `references` when needed). Claimed-authority bare sends die in P4.2 — this discharges the P4.1 rev-3 forward requirement. |
| D2 | **Schema v4:** `ALTER TABLE messages ADD COLUMN run_id TEXT` (nullable, ADD COLUMN-only); `Message.run_id: str \| None = None`; codec roundtrip extended; v1 untouched, migration chain v1→v2→v3→v4 converges. No FK constraint (house style — linkage validated at the bus boundary, D1). |
| D3 | **Resolver (production):** `relay/core/resolver.py::ConfigRoleResolver(mapping, known_agents)` implements the P4.1 `RoleResolver` Protocol — `resolve_role` = deterministic mapping lookup (unknown → `None` → existing bus rejection), `knows_agent` = membership in the configured agent set. Pure data + config; core stays registry-free (C.1/architecture test hold). |
| D4 | **Config surface (AMENDED rev 2 — fully decoupled):** new `roles:` mapping in `relay.yaml` — key = role address (MUST be a valid `AgentRole` value), value = configured agent name (MUST exist under `agents:`). **No coupling to the P3.3 top-level `reviewer:` selector**: no implicit fallback in either direction, no equality/conflict validation; a `roles.reviewer` entry MAY coexist with a different `reviewer:` target. Each remains the sole source of truth for its own workflow — `reviewer:` selects the P3 build-flow reviewer; `roles:` is the conversation-bus role vocabulary. `reviewer:` semantics untouched (P3.3 frozen). |
| D5 | **Role vocabulary (user-frozen, rev 1):** role addresses are `AgentRole` enum values only (`planner`, `reviewer`, `critic`, …). Config keys, resolver keys, and delivery role conversion all speak the enum; additive enum growth (P5/P6 roles) is the extension path. |
| D6 | **Agent factory seam:** `AgentFactory` Protocol — `build(name) -> Agent`, `model_of(name) -> str \| None` (keeps `Run.model` = requested model, P2.2 discipline). Production helper `relay/agents/factory.py::build_agent_factory(config, workspace_root)` wraps `registry.build_agent` (the agents package MAY import the registry; core never sees it). Tests inject fakes directly or via the helper + `transient_adapters`. |
| D7 | **Delivery service (AMENDED rev 2):** `relay/core/delivery.py::MessageDelivery(store, writer, factory)`; `async deliver(message_id) -> DeliveryOutcome`. Order: load persisted Message (typed `DeliveryRefusal` when absent / recipient not a bare logical-agent identity / recipient role value not a valid `AgentRole` / factory build fails — nothing persisted on any refusal) → build `AgentRequest` (role = `AgentRole(recipient_role)` when role-addressed, else `PARTICIPANT`; task/room copied; **`context_refs = message.references` verbatim**; prompt = the frozen deterministic envelope, D15) → harness recipients bound to a per-delivery READ_ONLY instance (D8) → `run_ask(..., agent_name=recipient, model=factory.model_of(recipient), pre_provider=<delivery binding hook>)`. The hook (D14/D13) inserts the MESSAGE_DELIVERED marker atomically in Tx1 and vetoes duplicates. Delivery never raises for run failures (spine records them); pre-run refusals and duplicate vetoes are typed exceptions. |
| D8 | **Delivery grant (AMENDED rev 2 — implementation frozen):** harness delivery ALWAYS constructs/uses a per-delivery `READ_ONLY_ACCESS` instance: configured profile present ⇒ `profile.model_copy(update={"grant": READ_ONLY_ACCESS})` (executable_path/extra_args/timeout preserved); profile absent ⇒ a fresh explicit READ_ONLY profile — **never** the adapter default and **never** the configured write grant. If the harness cannot honor READ_ONLY, the existing fail-closed pre-spawn grant translation refuses typed — and delivery MUST NOT fall back or retry with the configured grant (one attempt, honest failure). Negative authority test mandatory (G4). Deliberately NOT unified with `_planner_for` (which falls back to the adapter default when profile is None — P3.1 behavior unchanged). API recipients unaffected. |
| D9 | **No reply persistence (user-frozen, rev 1):** delivery writes NO Message rows — the recipient's output lands as the spine's `run_output` artifact. Reply persistence + linkage representation is P4.3's decision. Consequence: a P4.2 delivery's store delta is runs + events only (proven by test). |
| D10 | **`MESSAGE_DELIVERED` = binding-at-initiation (BLOCKER FIX, rev 2):** the marker means "Relay bound this persisted Message to this concrete recipient Run" — it is NOT success-only. It is persisted **atomically inside `run_ask`'s pre-provider Tx1**, in the same BEGIN IMMEDIATE transaction as `Run(RUNNING)`, the `run_input` artifact, and `AGENT_RUN_STARTED`, via the D14 hook. References: `message:<id>` + `run:<id>` + the source message's room/task scope; the entry's `room_id`/`task_id` fields carry the source message's scope. `sender="relay:delivery"`, `recipient=message.recipient`, bounded content metadata (type, sender→recipient, role note) phrased as a binding ("bound to run"), not a success claim. Failed/timeout/crashed runs RETAIN the marker; the run row + `AGENT_RUN_FINISHED` record the outcome. Additive EventType member — A.2 disjointness holds. Feed: zero changes — events compose generically and delivery markers render as system entries (correctly NOT deduped). |
| D11 | **Direct-addressed delivery role (rev 1):** additive `AgentRole.PARTICIPANT = "participant"` for direct (non-role-addressed) deliveries; role-addressed deliveries use the addressed role. A persisted-but-bogus `recipient_role` (possible only via resolver-less P4.1-style sends) is a typed delivery refusal, never a crash. |
| D12 | **Boundary proofs (AMENDED rev 2):** AST authority-boundary test now covers `delivery.py` + `resolver.py` (import neither `state_machine`, `evidence`, nor `permissions` directly; orchestration plumbing arrives transitively via `relay.core.orchestrator` — same documented pattern as storage transitively for the bus). Behavioral delivery proof: task state, evidence, approvals, decisions byte-identical; per COMPLETED delivery attempt the counts delta is exactly +1 run, +1 `run_input` artifact, +3 events (`AGENT_RUN_STARTED` + `MESSAGE_DELIVERED` in Tx1, `AGENT_RUN_FINISHED` in the final Tx), +1 `run_output` artifact when the run succeeds, +0 messages. Tx1 atomicity proven: a simulated crash/failure between Tx1 and provider I/O leaves marker + RUNNING run — honestly "initiated, outcome pending". `run_ask` without the hook is byte-identical (existing spine tests green untouched). |
| D13 | **At-most-once delivery initiation — unconditional (FROZEN rev 3):** `MessageDelivery` guarantees at-most-once initiation per persisted Message, with NO escape hatch. The duplicate check (existing MESSAGE_DELIVERED markers referencing `message:<id>`) and the marker insert execute inside the SAME BEGIN IMMEDIATE boundary — run_ask's Tx1 via the D14 hook — so concurrent deliveries for one message are serialized by the SQLite write lock: the second transaction observes the first's committed marker and vetoes (typed `DuplicateDeliveryRefusal`, transaction rolls back, NOTHING persisted). Detection is crash-safe: a crash after initiation leaves the marker, blocking ALL re-initiation — after a successful run, a failed run, and the crash-pending window alike. The rev-2 `force=True` escape hatch is REMOVED: redelivery/retry semantics (retry the same Message, require a new Message, or driver-owned override mechanics) are deliberately undefined in P4.2 and belong to P4.4/later work, addable explicitly then. `deliveries_for_message(message_id)` read helper still provided — read-only observability for the driver, never an override path. |
| D14 | **`run_ask` pre-provider seam (NEW rev 2 — the only orchestrator change):** additive, opt-in keyword parameter `pre_provider: Callable[[Run, Artifact], Iterable[EventLogEntry]] | None = None`. When supplied, the callable is invoked INSIDE Tx1 after the run row and `run_input` artifact are staged; its returned entries are recorded in the same transaction (MESSAGE_DELIVERED). The callable may raise to VETO: the exception propagates through the transaction context (atomic rollback — no run, no artifact, no events) and out of `run_ask` to the caller. Contract split documented: provider-I/O failures → `AskOutcome` (spine owns them, "never raises" preserved); pre-provider hook exceptions → CALLER-authored refusals that surface typed after a clean rollback. Default `None` = byte-identical behavior for every existing caller (`relay ask`, `run_build`). No TaskState, no `run_build`, no other orchestrator logic changes. |
| D15 | **Deterministic delivery envelope (NEW rev 2):** the delivery prompt is a frozen, deterministic template carrying at least `sender` + `MessageType` + `content` (plus the `blocking` flag), in a fixed field order — byte-for-byte assertable: the same Message always produces the identical prompt; no timestamps, no run ids, no transcript. Semantic references are NOT rendered into the prose: `message.references` pass through to `AgentRequest.context_refs` verbatim (existing field); whether an adapter consumes `context_refs` is adapter policy — references remain canonical on the Message row, and D.10 reconstruction is explicitly NOT implemented here. Envelope is bounded by construction (content ≤ 50k send-time cap, D12-P4.1; template static-size). |

## 4. Acceptance gates

* **G1 Additivity:** v3→v4 migration preserves all rows; fresh DB lands at v4;
  `run_id` codec roundtrip; existing migration/append-only/hygiene tests green
  untouched.
* **G2 Authorship matrix (all typed, all pre-persistence, store byte-identical on
  rejection):** bare sender without `run_id` rejected; prefix sender WITH `run_id`
  rejected; unknown run id rejected; `run.agent != sender` rejected; valid linkage
  accepted (exactly-at-boundary case: `run.agent == sender`). No pairing cases (P4.3).
* **G3 Resolution:** role→agent resolution through `ConfigRoleResolver` end-to-end
  at the bus (send persists resolved recipient + `recipient_role`, P4.1 D3 shape);
  unresolved role typed rejection; `knows_agent` hardening (unknown bare sender
  rejected — P4.1 behavior now production-backed); config validation: bad role key,
  unknown agent target → `ConfigError`; `roles:`/`reviewer:` divergence explicitly
  ACCEPTED (a test pins that differing targets coexist without error — D4).
* **G4 Delivery:** heterogeneous day one — same delivery path over an API-fake and
  a harness-fake recipient. **Binding semantics:** MESSAGE_DELIVERED committed in
  Tx1 (same transaction as Run(RUNNING) + run_input + AGENT_RUN_STARTED) with
  `message:`/`run:` refs + source scope, present for success AND failure; failed
  runs honestly FAILED via spine records. **At-most-once (unconditional):**
  second `deliver()` on the same message → typed `DuplicateDeliveryRefusal`,
  zero store delta — proven after a successful run, after a FAILED run, and
  after the crash-pending window alike; NO override parameter or path exists
  (rev 3); sequential double-delivery proves the check+marker share
  one BEGIN IMMEDIATE boundary (nested transactions impossible — audit fact).
  **Authority:** harness recipient configured `workspace_write` receives a
  per-delivery READ_ONLY profile (asserted on the profile the run actually used);
  **negative authority test:** a harness that cannot honor READ_ONLY refuses typed
  pre-spawn and delivery never falls back to the configured write grant (no second
  run, no write grant ever passed). **Envelope:** byte-for-byte determinism (same
  message → identical prompt; fixed field order: sender, type, blocking, content);
  references appear in `context_refs`, not in the prose. Refusals (absent message,
  non-bare recipient, bogus role, factory failure) typed with nothing persisted.
  Counts delta per D12 (0 messages written by delivery); canonical state untouched.
* **G5 Architecture:** AST authority boundary extended to `delivery.py` +
  `resolver.py`; `run_ask` default-path byte-identity proven (existing spine tests
  green untouched); full suite green; ruff clean.

## 5. Non-goals

* No reply persistence, no reply-linkage representation, no reply-to-human
  surfacing (P4.3/P7 — a reply to a `human:`/`relay:` sender is unrepresentable as
  a bus recipient under frozen P4.1 D3; delivery to such messages still works,
  output lands in the run artifact).
* No budgets, no communication policy, no `blocking_key`, no round-trip
  accounting (P5); no blocking waits or paused-stage storage (Q-B, P6).
* No driver/loop, no redelivery/retry semantics of any kind — P4.2 freezes
  unconditional refusal of every re-initiation attempt (D13);
  retry-the-same-Message vs new-Message vs driver-owned mechanics are P4.4+
  explicit additions. No crash-recovery of initiated-but-unfinished deliveries
  (P4.4; read helper provided per D13).
* No D.10 context reconstruction engine — `context_refs` pass-through only
  (D15); recipient-side context policy is P4.4; the reconstruction engine is P7.
* No CLI surfaces; no seats/persistent Rooms (P7); no TaskState or `run_build`
  changes; orchestrator changes limited to the additive opt-in D14 seam (default
  byte-identical); no DB CHECK constraints.

## 6. Open items (carried)

* Delivery directive/envelope exact wording — the FIELD SET and order are frozen
  (D15); the template's human phrasing is an implementation detail, non-normative.
* Cross-task run/message consistency deliberately NOT enforced: authorship is
  identity-level (`run.agent == sender`); traffic scoping is the driver's concern
  (P4.4).
* Adapter consumption of `context_refs` is adapter policy; P4.2 guarantees only
  verbatim pass-through (D15) — consumption/reconstruction is P4.4/P7.
* Duplicate-marker query scans MESSAGE_DELIVERED-typed event rows (references are
  a JSON list); adequate at P4 scale — P4.4 may optimize (scope-filtered query).
* Redelivery/retry of a delivered Message (including a failed delivery) — P4.4+
  explicit addition; P4.2 neither provides nor reserves a mechanism (D13).
* Q-B paused-stage storage / crash-safety of blocking waits → P6 (unchanged).
* Unification of `roles:` with the P3.3 `reviewer:` binding, if ever wanted, is a
  P4.4/P6 product decision — P4.2 freezes their independence (D4), not a merge
  path.
