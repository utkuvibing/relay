# P6.3 — Resume parked builds: `relay continue`

Status: implemented; exit gate passed.

## Accepted scope

Make a parked `relay build` task resumable in a new process. The P6.2 loop
becomes an idempotent, ledger-driven stage driver shared by `run_build` and
the new `continue_build`; the ledger is the cursor and no in-memory state is
required to resume. Explicitly deferred: bounded micro-interactions inside
stages, reviewer retry, task lease/lock, HEAD-drift guard, baseline snapshot
GC, mid-run cancellation of harness children, new task states, schema
migration, and the remaining §23 budget fields.

## Ledger-driven driver

`relay/core/orchestrator.py::_drive_build` re-derives a read-only
`BuildPosition` (`relay/core/build_ledger.py::derive_position`) from durable
records at every iteration: persisted stage outputs make the step a pure
`advance` — no re-dispatch, no budget — while missing outputs run the stage
exactly once. Crash windows between two `advance_task` calls (plan freeze →
`PLAN_READY`, DIFF mint → `IMPLEMENTED` → `VERIFYING`, TESTS_PASSED →
`REVIEWING`) recover by construction. The P6.2 stop vocabulary is unchanged
(`LoopStopReason`); `budget_exhausted`/`no_workspace_change` still persist
`relay.build.loop.v1` with cumulative `fix_runs_used`. `BuildOutcome` gains
`resumed_from` and `prior_attempts`; `attempts` is cumulative across
invocations (identical to P6.2 for `build`). The DIFF artifact +
`IMPLEMENTATION_PRODUCED` evidence now mint atomically in one transaction.

## Build-run provenance

Every run the build driver dispatches — planner, implementer, fix, reviewer —
commits one `BUILD_RUN_DISPATCHED` binding marker (`sender="relay:build"`,
`task_id`, references `run:<id>`, `task:<id>`, `build_stage:<stage>` and, for
implement/fix, `build_attempt:<n>`) inside the run's pre-provider Tx1 via the
existing `run_ask(pre_provider=...)` seam — the same contract as P4.2's
`MESSAGE_DELIVERED`. The marker asserts a binding, never success; failed and
cancelled runs retain it.

`derive_position()` counts attempts and budgets only over marker-bound
implement/fix runs; `--settle-interrupted` settles only marker-bound
interrupted runs and task-bound verification `ToolRun`s. P4
`MESSAGE_DELIVERED`-bound runs are ignored everywhere. A task-scoped run
bound by neither marker refuses `unattributed_runs` — never a miscount.

## Budget semantics (dispatch-only, cumulative)

`fix_runs_used = max(0, attempts - 1)` is derived from the ledger across all
invocations. `budget.max_fix_loops` is consulted at exactly one point:
immediately before the driver creates a NEW implementer/fix run. Recovery of
persisted boundaries, verification of an existing DIFF, review, and PASS
promotion never consult the budget — an exhausted task whose latest attempt
already minted DIFF + `IMPLEMENTATION_PRODUCED` resumes through verification
and review with zero new implementer runs. `continue` refuses pre-execution
with `budget_exhausted` only when the derived next action is a new dispatch.

## Durable baseline

`.relay/baselines/<task_id>/` holds a canonical `manifest.json`
(`relay.build.baseline.manifest.v1`: `task_id`, `files {path: sha256}`,
`oversized_paths`) plus content-addressed `blobs/<sha256>`. Publication is
crash-safe: blobs and the manifest are built under `baselines/.staging/`
(tmp file → flush+fsync → `os.replace` per file, then staging-dir fsync),
published by one atomic directory rename onto the canonical path, then the
parent `baselines/` directory is fsynced (POSIX; best-effort on Windows).
Only then does the driver write the ledger pin — a `REPORT` artifact with
`relay.build.baseline.v1` (`task_id`, `manifest_digest`, `file_count`,
`oversized_count`) — so the database can never reference a snapshot whose
publication is not yet durable.

The baseline is captured at the exact P6.2 boundary: after plan freeze /
entry into `IMPLEMENTING`, before the first implementation run. Resume
verifies the pin's digest plus every blob up front, before any stage runs;
missing, partial, digest-mismatched or count-mismatched snapshots refuse
`baseline_corrupt` with zero persistence, and a pinned baseline is never
silently rebuilt. Pin absent with `attempts >= 1` refuses `no_baseline`.

## Durable request and pinned identity

`relay build` persists `relay.build.request.v1` (full prompt, pinned
implementer name, pinned model) as its first write after validation —
`Task.title` only keeps `prompt[:200]`. `relay continue` rebuilds the
implementer from the pinned name + pinned model; a pinned agent missing from
`relay.yaml` is a config error naming it. Verification, reviewer, approval
and budget come from CURRENT Relay config; `continue` takes no overrides.

## Interrupted runs

`continue` refuses `run_in_flight` when marker-bound `Run`s or task-bound
verification `ToolRun`s are still `RUNNING`, unless `--settle-interrupted`
settles them to `CANCELLED` (plus `AGENT_RUN_FINISHED`/`TOOL_COMPLETED`) in
one transaction — marker-bound runs only; P4-bound or unbound runs are never
touched. A settled implementer run still counts as an attempt; partial
workspace writes join the next cumulative DIFF. Additionally `run_ask` now
settles `asyncio.CancelledError` as `CANCELLED` instead of leaking `RUNNING`
(harness `HarnessCancelledError → FAILED` mapping unchanged).

## CLI

`relay continue [TASK_ID] [--settle-interrupted]` — no topic/agent/model
overrides. `TASK_ID` resolves by exact id or unique prefix; omitted selects
the most recent non-`DONE` task. Pre-execution refusals persist nothing:
`DONE` → terminal; `APPROVAL_REQUIRED` → approve hint; `no_request`,
`unattributed_runs`, `ledger_inconsistent`, `run_in_flight`, `no_baseline`,
`baseline_corrupt`; `budget_exhausted` only when a new dispatch is required.
A first-ever baseline capture additionally requires a clean worktree (the
same rule as `build`); a pinned baseline permits the parked workspace.
Outcome renders via the shared build renderer plus a
`resumed from <state>` note and cumulative `attempts N (M prior)`.

## Acceptance

- Exhausted budget + already-persisted DIFF/evidence ⇒ `continue` advances
  the boundary, verifies, reviews, and promotes PASS with zero new
  implementer runs; the review pins the prior attempt's run/diff/verification.
- Exhausted budget + a real new fix needed ⇒ `continue` refuses
  pre-execution with zero store delta; raising `max_fix_loops` resumes with
  exactly one more fix dispatch fed by the persisted packet.
- Unrelated P4 task-scoped `IMPLEMENTER` runs (deliveries) never count
  toward attempts/budget, never block `continue`, and are never settled by
  `--settle-interrupted`.
- Corrupt/missing baseline (blob digest/missing, manifest digest/missing/
  invalid, count mismatch) fails closed with zero delta — including from a
  `REVIEWING` park — and a pin-less leftover snapshot is only ever replaced
  while `attempts == 0`.
- Publish order is asserted: blobs+manifest staged, atomic rename, parent-dir
  fsync, then — and only then — the ledger pin; a crash before the pin leaves
  a replaceable pin-less snapshot.
- Every run a build dispatches carries exactly one `BUILD_RUN_DISPATCHED`
  marker committed in Tx1 (visible even for FAILED/CANCELLED runs).
- Interrupted-boundary resumes (context/plan/freeze/diff-mint/verification/
  review windows) complete with no duplicate runs, artifacts, or evidence.
- `run_ask` settles `CancelledError` as `CANCELLED`; DIFF + evidence mint is
  atomic under injected faults.
- All P6.2 loop tests pass with unchanged run-role sequences, transition
  events, and loop records.
