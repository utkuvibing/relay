# P5.3 — Durable staged protocol runner

Status: implemented; exit gate passed.

## Scope and accepted decisions

P5.3 adds ordered execution, configured role/capability binding, prior-stage
context, definition/configuration pinning, durable resume, and fixed repetition.
It reuses P5.2 admission, facts, and evaluators and the existing delivery spine.
The P4 driver and its identities are unchanged. No CLI, escalation UX, semantic
convergence detection, automatic fallback, retries, or canonical workflow-state
mutations are added. CLI/escalation UX remains P5.4.

One optional `repeat: {stages: [...], rounds: N}` declares a contiguous, ordered,
unique stage block. Strict integer rounds range from 1 to 100; omission preserves
single-pass execution. `protocol_schedule()` expands the finite schedule with
stage-local occurrence indexes. The existing stage-key algorithm is unchanged.
Pure protocol evaluation accepts an ordered prefix of this expanded schedule.

## Runtime API and behavior

`ProtocolRunner(store, writer, factory, bindings, policy)` exposes asynchronous
`start(ProtocolSpec(...))` and `resume(execution_id)`. The factory and binding
source must describe the same configuration; `RegistryAgentFactory` implements
both interfaces. Store, writer, and policy must use the same ledger, as required
by the existing conversation services.

```python
factory = RegistryAgentFactory(config, workspace_root)
runner = ProtocolRunner(store, writer, factory, factory, policy)
result = await runner.start(ProtocolSpec(
    definition=load_protocol("protocols/debate.yaml"),
    execution_key="design-review-1",
    topic="Review the proposed design",
    room_id=room.id,
))
result = await runner.resume(result.execution_id)
```

The result includes execution identity, stage evaluations, canonical output IDs,
protocol evaluation, a typed stop reason, and refusal details when available.
Stop reasons are `complete`, `delivery_pending`, `request_failed`,
`policy_refused`, `budget_exhausted`, and `input_refused`.

- All declared roles resolve before execution creation; required capabilities
  must be explicitly advertised. Factory projection performs no provider call,
  binary discovery, or authentication probe. Delivery retains its read-only grant.
- Participants execute in declaration order. Requests are nonblocking `note`
  messages from `relay:protocol`, requesting each role's declared output type.
  Start preflight validates the stage request/reply schedule.
- Persisted JSON request content contains topic, stage, occurrence, role,
  expected output, and prior canonical outputs with source IDs, authors, types,
  and exact text. Message references carry those source IDs too. All participants
  in an occurrence get the same prior-output snapshot, excluding current-stage
  replies. Initial analysis is therefore independent. No unrelated transcript is
  fetched and no text is silently summarized or truncated; the existing bus
  content-size cap returns a refusal if accumulated context is too large.
- Fresh requests use deterministic IDs and semantic equality checks. Duplicate
  starts use one short `BEGIN IMMEDIATE` transaction. Request races converge on
  the message primary key; delivery Tx1 checks duplicate admission before budgets.
  No database transaction spans a provider call. A refused delivery may leave its
  durable, unspent request for subsequent same-key re-entry.
- Resume reconstructs progress from requests, delivery bindings, Runs, replies,
  and validated stage facts. A succeeded Run can materialize its missing reply
  without spending another turn, including at the final budget boundary.
  Running deliveries return pending without polling. Failed/cancelled required
  requests stop execution and are not retried. Completion wins over exhaustion.
- Stage budgets apply per occurrence; workspace aggregate limits span stages
  and rounds. The example's three critique/rebuttal rounds require 22 turns
  (3 analysis + 18 critique/rebuttal + 1 synthesis). The caller must provide
  sufficient aggregate allowance; the runner never raises policy budgets.

## Durable records and exact nullable uniqueness

Schema v7 adds `protocol_executions` and `ProtocolExecution`: ID, execution key,
nullable scope, topic, definition snapshot/digest, bindings snapshot, runner
version, and creation time. Model fields are immutable scalars. UPDATE and
DELETE are refused by both database triggers and the store API.

Three partial unique indexes enforce `(execution_key, exact scope)`:

| Indexed columns | Predicate |
| --- | --- |
| execution_key, room_id, task_id | room_id IS NOT NULL AND task_id IS NOT NULL |
| execution_key, room_id | room_id IS NOT NULL AND task_id IS NULL |
| execution_key, task_id | room_id IS NULL AND task_id IS NOT NULL |

A database CHECK rejects both-null scope. SQL NULL and the literal `"null"`
remain distinct. Historical v6 rows are untouched. No mutable progress cursor
or new event vocabulary is introduced.

Identical starts reuse the record; changed topic, definition (including budgets),
bindings, or fingerprints refuse. Resume reads the saved definition, verifies its
encoding/digest, and checks current participant fingerprints. It does not require
the original YAML. Already admitted reply recovery retains the existing policy
guarantees; current policy controls fresh spending.

## Frozen v1 canonical encodings

All encodings use UTF-8 bytes of
`json.dumps(value, ensure_ascii=True, separators=(",", ":"), allow_nan=False)`.
SHA-256 hashes those exact bytes. Arrays have fixed positions; enum values are
strings; optional values are JSON null. Strings are preserved exactly without
trimming, Unicode normalization, path resolution, or endpoint normalization.
Changing an encoding requires a new version and explicit compatibility handling.

### Protocol definition

Digest prefix: `protocol-definition:v1:`. The persisted snapshot is exactly the
canonical byte sequence decoded as UTF-8. Decode reconstructs the validated
definition, re-encodes it, and verifies both canonical equality and the digest.

```text
["relay.protocol.definition.v1", name, version,
 [[role, [required_capability, ...]], ...],
 [[stage_id, [participant_role, ...],
   [[sender_role, recipient_role, [message_type, ...], blocking_allowed], ...],
   [allowed_type, ...], [max_agent_turns, max_blocking_messages],
   [[role, output_type], ...], [require_synthesis, early_stop_on_answered]], ...],
 [protocol_require_synthesis],
 null | [[repeat_stage_id, ...], rounds]]
```

Explicit defaults and declaration order are retained. YAML whitespace, comments,
mapping-key order, source paths, and omitted-versus-explicit defaults do not
affect the digest.

### Participant configuration

Fingerprint prefix: `participant-config:v1:`.

```text
["relay.protocol.participant-config.v1", logical_agent, backend, adapter,
 requested_model, api_endpoint, harness_executable_selection, timeout,
 auth_probe, [sorted_unique_capability, ...], effective_grant, workspace_root]
```

The factory projects resolved settings and effective read-only delivery profile;
timeout is encoded as a finite float, e.g. `300.0`. Inapplicable fields are null.
Null endpoint/executable selection denotes the adapter default, without probing
it. An absent harness profile uses existing profile defaults. Configured write
grants do not change the projection because discussion delivery always substitutes
`read_only`. Workspace root is explicitly allowlisted because it changes harness
execution context. This pins configuration, not binary contents or authentication
state.

Arbitrary `extra_args` and endpoints with userinfo, query, or fragment are refused
before persistence; no generic serialization fallback exists. Credentials,
environment contents, unrelated configuration, and raw argument blobs are never
projected. Only role, logical-agent name, and fingerprint enter the execution's
bindings snapshot, encoded as `["relay.protocol.bindings.v1", [[role, agent,
fingerprint], ...]]` in protocol participant order.

### Runner request identity

Message ID prefix: `protocol-request:v1:`.

```text
["relay.protocol.request.v1", execution_id, stage_key, participant_role]
```

The runner format is `relay.protocol.runner.v1`; it governs deterministic request
content construction as well. Re-entry verifies all persisted message fields
except creation time against the expected resolved request. P4 identity vectors
are untouched.
