# P7.1 — Persistent Room lifecycle and stable seats

Status: implemented; P7.1 exit gate passed.

## Scope

Deliver durable Room lifecycle, workspace-local current-Room selection,
stable role seats with rebindable logical-agent bindings, and one canonical
chronological Room feed. Closing is a reversible Room-level traffic fence:
it preserves canonical state and tasks but refuses new Room messages and
protocol activity until the Room is resumed.

Deferred: targeted chat, context reconstruction, plan/decision/finding graphs,
external-session continuation, seat removal, and other later-P7 work.

## Interfaces

- `relay room create <name>` snapshots every configured `roles:` binding,
  requires at least one role, creates an open Room, and makes it current.
- `relay room list` shows all current-workspace Rooms with current marker,
  ID, name, status, and seat count.
- `relay room resume <room>` reopens/selects a Room and renders its roster and
  canonical feed without invoking an agent.
- `relay room close <room>` closes the Room and clears it as current.
- `relay room bind <room> <role> <agent>` creates or rebinds a stable role
  seat. The role must be an existing `AgentRole`; the agent must exist under
  `relay.yaml`'s `agents:` mapping. Refusal is mutation-free.
- Room lookup precedence is exact ID, case-insensitive exact name, then unique
  ID prefix. Seat identity is `(room_id, role)`; provider/model/backend facts
  are never identity.

## Canonical Room feed

The provider-free, read-only Room feed independently enumerates all Room
Messages and all Room-scoped `MESSAGE_SENT` events before rendering. It
requires an exact one-to-one mapping: each Message has exactly one marker;
each marker has exactly one `message:<id>` reference resolving to a Message
in the same Room; and no Message has multiple markers. Orphan Messages,
orphan markers, duplicate markers, multiple message references, cross-Room
references, and contradictory linkage are integrity failures detected before
returning any feed items.

The event log sequence is authoritative ordering. A `MESSAGE_SENT` position
renders the canonical Message payload once, not the marker text. All other
Room-scoped system events render directly at their sequence, including Room
create/resume/close/bind lifecycle events. Feed projection performs no writes,
invocations, transitions, or derived-state persistence.

## Persistence and fences

- Schema v8 adds Room status/timestamps, `Workspace.active_room_id`, lookup
  indexes, and Unicode-canonical case-insensitive Room-name uniqueness per
  non-null workspace.
- Legacy Rooms become open without ID/history changes. Legacy name collisions
  are repaired in `(created_at, id)` order: the first keeps its name and later
  entries take the lowest unused ` (n)` suffix before the unique index lands.
- `Room.members` remains the sole seat representation, with one valid role per
  Room enforced through the lifecycle module.
- Create/resume/close/bind persist their Room/workspace changes and lifecycle
  event atomically. Already-satisfied operations are event-free no-ops.
- `ConversationBus.send` reloads and verifies an OPEN Room inside the same
  `BEGIN IMMEDIATE` transaction immediately before the Message and marker
  inserts. Thus close and send serialize without a post-close write.
- Protocol start/resume against a closed Room refuses before agent invocation
  and without any new Room-scoped execution, Message, Run, or outcome event.
  The refusal itself creates no feed traffic and existing history is untouched.
- `relay discuss` creates managed open Rooms and deterministically suffixes
  repeated topic names. Existing protocol binding snapshots remain immutable.
- `relay status` shows the current Room. Close never completes/cancels a Task.
