# P6.2 — Bounded fix loop

Status: implemented; exit gate passed.

## Accepted scope

Execute the fix half of the Phase 6 loop inside one `relay build` invocation:
review findings or a failed verification re-enter `IMPLEMENTING` and dispatch
a bounded number of fix runs through the same configured implementer adapter
(`role=IMPLEMENTER`, the same crash-safe `run_ask` spine). Explicitly
deferred: resume/`relay continue` and re-driving parked tasks; bounded
micro-interactions inside stages; discussion-bus integration for the loop;
reviewer retry after process failure or malformed output; semantic
convergence detection; new task states; schema migration; the remaining §23
budget fields.

## Loop and blocking inputs

```text
Plan → Implement → Verify → Review
                         ↓ findings / test failure
                       Fix → Verify → Review
```

- Attempt 1 uses the existing implement directive; attempts 2+ use a fix
  directive embedding the canonical plan, the pending blocking input, and the
  original request. The blocking input is the canonical `FIX_PACKET` after
  findings, or the failed `TEST_RESULT` artifact after a failed exam —
  persisted bytes, embedded verbatim, never regenerated.
- One baseline is captured immediately before the first implementation run
  and serves every attempt: every DIFF is cumulative against it, so a later
  PASS certifies the complete workspace change rather than the last delta.
- Only a fresh, non-empty cumulative diff mints a DIFF artifact and
  `IMPLEMENTATION_PRODUCED`. An empty diff mints nothing; a byte-identical
  diff to the previous attempt counts as no progress (the §24 "no new
  evidence" condition in deterministic form).
- Each attempt re-runs Relay-scoped verification and re-runs the review with
  rebuilt `ReviewInputs`, so every review pins its own attempt's exact run,
  diff, tool-run, evidence, and test-result ids — no schema change needed.

## Budget and accounting

```yaml
budget:
  max_fix_loops: 3
```

- Default `3`; `0` preserves the P6.1 one-pass behavior exactly.
- `budget:` is a new strict top-level section (`extra="forbid"`).
  `max_agents_per_task`, `max_discussion_rounds`, `stop_on_consensus` and any
  other key are config errors, not silently accepted future vocabulary.
- `attempts` counts dispatched implementation/fix runs only; the planner
  never counts (planning failure ⇒ `attempts == 0`). With the default bound
  a build dispatches at most 4 impl/fix runs: `fix_runs_used ==
  max(0, attempts - 1)`; worst case is 9 agent runs (1 planner, 4 impl/fix,
  4 reviewer) plus 4 Relay-owned verification executions.

## Stop reasons and outcome semantics

Deterministic `LoopStopReason` vocabulary: `pass_promoted`,
`budget_exhausted`, `no_workspace_change`, `run_failed`,
`verification_blocked`, `review_blocked`, `loop_disabled`,
`no_blocking_input`.

`BuildOutcome` is latest-attempt: `ask`, `diff_artifact_id`, and
`tool_run_ids` describe the last impl/fix run actually dispatched; `review`
is the latest review result; a new `planner` field carries the planning
outcome so planning failure renders correctly with `attempts == 0`. After a
no-progress final attempt `diff_artifact_id` is `None`; the reachable
cumulative diff survives on the loop record.

`budget_exhausted` and `no_workspace_change` persist a `REPORT` artifact with
canonical `relay.build.loop.v1` payload (`task_id`, `reason`,
`fix_runs_used`, `last_review_artifact_id`, `last_fix_packet_artifact_id`,
`last_diff_artifact_id`) — a diagnostic observation only: no evidence, no
transition, same pattern as the invalid-review report. The task remains
parked at `IMPLEMENTING`; `verification_blocked` parks at `VERIFYING`;
reviewer failure or malformed output parks at `REVIEWING` with no retry.

Interruption is boundary-only: stop conditions are evaluated at stage
boundaries, never mid-run. A crash mid-loop leaves durable run history and an
honestly parked task.

## CLI

`relay build` renders the latest attempt (status/output/error, observed
ToolRuns, DIFF id), the latest review result, the attempt count, and the loop
stop reason; planning failure still renders via the planner outcome when no
impl/fix run was dispatched.

## Acceptance

- Findings → fix → re-verify → re-review → PASS reaches
  `APPROVAL_REQUIRED` with the second review pinning the fix attempt's
  run/diff/verification records; `attempts == 2`.
- `max_fix_loops: 1` permits exactly two impl/fix runs, then parks at
  `IMPLEMENTING` with `fix_runs_used: 1` on the loop record.
- The default bound permits four attempts, four reviews, four DIFFs, and
  `fix_runs_used: 3` before exhaustion.
- `max_fix_loops: 0` is byte-compatible with P6.1 (one pass, `loop_disabled`,
  no loop record).
- A failed exam feeds the fixer its persisted `TEST_RESULT`; the passing
  review pins the post-fix verification records.
- A byte-identical fix stops at `no_workspace_change` — no second DIFF, no
  second `IMPLEMENTATION_PRODUCED`, no second review; the record's
  `last_diff_artifact_id` still resolves.
- Reviewer crash/malformed output mid-loop parks at `REVIEWING` with exactly
  one failed run — never retried.
- Mid-loop findings promotions and the post-loop PASS promotion roll back
  atomically under injected faults.
- Config validation rejects unsupported budget keys, non-integer values, and
  negative bounds.
