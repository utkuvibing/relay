## 0. Scope & Delta from rev 1

### In Scope
1. **Schema v5:** Additive `messages.reply_to_id TEXT NULL`, indexed via `idx_messages_reply_to` (indexed lookups), plus a partial unique index `idx_messages_unique_reply_run` enforcing at most one generated reply per `(reply_to_id, run_id)` pairing at the database level.
2. **First-class structural reply linkage (`Message.reply_to_id`):** Validated at the bus boundary with parent existence check, exact scope equality, sender/recipient symmetry, and cycle-safe depth bounding. All sender/type communication policy is deferred to P5.
3. **Recipient addressing expansion:** Bus accepts `human:*` and `relay:*` recipients alongside bare logical agents (enabling agent replies to human/system messages).
4. **P4.1 self-send invariant preserved:** Reject self-send for bare logical-agent identities only; prefix senders (`human:*`, `relay:*`) are not constrained by self-send.
5. **Delivery refusal boundary preserved:** `MessageDelivery` continues to execute *only* bare logical-agent recipients; delivery to `human:*` or `relay:*` remains strictly refused.
6. **Decoupled reply materialization (`deliver_and_reply`):** Dedicated API that delivers an incoming message, observes the durable `run_output` artifact, verifies dual provenance (authorship + `MESSAGE_DELIVERED` causal binding), and persists the reply in a separate post-run transaction.
7. **Crash recovery & idempotent materialization:** Recovery from crashes in the post-provider window (Run succeeded + output committed, but Relay died before reply insert) reconstructing a minimal successful `AgentResponse` and returning `AskOutcome(run=run, response=recovered_response)` without re-invoking the agent.
8. **Narrow answering semantics:** `clarification_request -> clarification_response` is the sole canonical answering pair in P4.3; other replies may link structurally but do not mark a blocking request answered.
9. **Communication answering vs. workflow resolution:** Strict separation between communication-level queries (`has_answering_reply`, `unanswered_blocking_messages`) and workflow-level stage advancement (P6).
10. **Hard thread ceiling:** Protocol-independent thread depth bound (`DEFAULT_MAX_THREAD_DEPTH = 10`), strictly distinct from P5 communication budgets.
11. **Cycle-safe indexed queries:** Direct SQL-indexed queries for child replies, unanswered blocking messages, and bounded, cycle-safe `reply_chain()` and write-path depth traversals.
12. **D.8 authority boundary proof:** Structural AST and behavioral verification that reply traffic cannot mutate TaskState, Evidence, Approval, Decision, or policy.

### Explicitly Out of Scope
* P5 protocol budgets, per-stage clarification limits, communication policies, and communication permission matrices.
* P6 semantic execution loop, stage resume dispatch, and promotion of replies to canonical `Decision` / `Plan` records.
* P7 persistent Room UX, seats persistence, and `@role` chat addressing syntax.
* Generic message redelivery, retries for failed runs, or dead-letter queues.

## 1. Code Audit & Facts This Builds On

* **P4.1 bus core (`relay/core/bus.py`):** The bus is the single write path for messages, persisting `Message` and `MESSAGE_SENT` in one `BEGIN IMMEDIATE` transaction. Messages are append-only at both layers (Python `_APPEND_ONLY_TABLES` + SQLite triggers).
* **P4.2 delivery spine (`relay/core/delivery.py`):** `MessageDelivery.deliver()` binds a message to an agent Run inside Tx1 before provider I/O (`MESSAGE_DELIVERED` marker + `Run(RUNNING)` + `run_input`). It enforces at-most-once delivery initiation. `D9` explicitly states delivery writes zero Message rows; recipient output lands as the spine's `run_output` artifact.
* **Provider I/O is non-transactional:** `run_ask` commits Tx1, drops the database transaction, runs provider/harness I/O, then commits the final Tx (`Run(SUCCEEDED)` + `run_output` artifact). A database transaction can never span provider execution.
* **Delivery binding provenance:** `MESSAGE_DELIVERED` markers carry `references = [f"message:{message.id}", f"run:{run.id}", ...]`. The delivery run for any message can be discovered by filtering events where `ref == f"message:{message_id}"`.
* **Run output durability:** Successful runs always persist an `Artifact(kind=ArtifactKind.RUN_OUTPUT, run_id=run.id, content=...)` in the final Tx of `run_ask`.

## 2. Frozen Decisions (D1–D16)

| # | Decision | Architectural Rationale & Invariants |
|---|---|---|
| **D1** | **Schema v5 migration** | `ALTER TABLE messages ADD COLUMN reply_to_id TEXT` (nullable, ADD COLUMN-only). Historical messages load with `reply_to_id = None`. No self-referential foreign key constraint (see Migration Review below); parent existence is strictly validated at the bus boundary. |
| **D2** | **Reply index & uniqueness constraint** | Two indices added in v5: (1) `CREATE INDEX IF NOT EXISTS idx_messages_reply_to ON messages(reply_to_id)` for indexed lookups; (2) `CREATE UNIQUE INDEX IF NOT EXISTS idx_messages_unique_reply_run ON messages(reply_to_id, run_id) WHERE reply_to_id IS NOT NULL AND run_id IS NOT NULL`. Enforces at the database engine level that one delivery Run can materialize at most one direct reply Message for a parent. |
| **D3** | **Parent existence & append-only immutability** | If `message.reply_to_id` is set, `parent = store.load_model(Message, message.reply_to_id)` must resolve. Because `messages` is append-only, a parent must exist *before* a child can reference it. Self-reply (`message.id == message.reply_to_id`) and forward references are impossible by construction. |
| **D4** | **Exact scope inheritance** | A reply must preserve parent scope exactly: `reply.room_id == parent.room_id` AND `reply.task_id == parent.task_id`. A reply may not add, remove, or swap room or task scope. Violations raise `ReplyScopeMismatch`. |
| **D5** | **Addressing symmetry** | A reply's recipient must match the parent's sender: `reply.recipient == parent.sender`. The reply's sender must match the parent's intended recipient: (a) if parent had direct `recipient`, `reply.sender == parent.recipient`; (b) if parent was role-addressed, `reply.sender` must match the parent's resolved `recipient`. |
| **D6** | **Recipient expansion for human & relay** | `ConversationBus._validate_recipient` is expanded to accept: (1) bare logical-agent identities (`knows_agent` verified when resolver present); (2) `human:*` identifiers; (3) `relay:*` identifiers. Enables agents to address replies to human users or Relay system components. |
| **D7** | **P4.1 self-send invariant preserved** | Direct self-send (`sender == recipient`) is rejected *only* for bare logical-agent identities (`if ":" not in message.sender and message.recipient == message.sender`). Prefix senders (`human:*`, `relay:*`) are not constrained by self-send, exactly preserving P4.1 D14. |
| **D8** | **Delivery refusal boundary preserved** | `MessageDelivery.deliver()` and `deliver_and_reply()` continue to require bare logical-agent recipients. Calling delivery on a message whose recipient starts with `human:` or `relay:` raises `DeliveryRefusal`. Non-agent participants are conversation endpoints, never buildable execution harnesses. |
| **D9** | **Structural reply linkage (P5 policy deferred)** | P4.3 enforces only structural validity: parent exists, exact scope equality, sender/recipient symmetry, and cycle-safe depth bounding. All broad semantic child-type matrices are removed from P4.3 and deferred to P5 communication policy. Existing invariants hold: `MessageType.SYSTEM` remains reserved for `relay:*`, and `note` cannot be `blocking=True`. |
| **D10** | **Narrow canonical answering semantics** | `clarification_request -> clarification_response` is the sole canonical answering pair in P4.3. Other replies may be linked structurally (e.g. `clarification_request -> challenge` or `challenge -> rebuttal`), but they do *not* automatically count as answering/resolving a blocking request in P4.3 queries. |
| **D11** | **Communication answering is not workflow authority** | Querying `has_answering_reply(message_id)` or `unanswered_blocking_messages(...)` reports communication state only. Mere arrival of an answer does NOT mutate `TaskState`, clear approval gates, or authorize stage advancement. Canonical promotion (Decision, Plan revision) and scheduler resumption remain strictly under P6 and state machine authority (SPEC D.4, D.8). |
| **D12** | **Hard thread ceiling & cycle-safe write path** | Protocol-independent depth bound: `depth(msg) = 0 if msg.reply_to_id is None else depth(parent) + 1`. Default: `DEFAULT_MAX_THREAD_DEPTH = 10`. The write-path traversal is cycle-safe and bounded: corrupt/cyclic ancestry raises typed `ReplyRejected` with zero persistence. Exceeding depth raises `RoundTripLimitExceeded`. Distinct from P5 per-stage communication budgets. |
| **D13** | **Decoupled reply materialization (`deliver_and_reply`)** | Distinct API from `deliver()`. Executes in two distinct phases: (1) invoke `self.deliver(message_id)` (Tx1 commit, provider execution, final run Tx commit); (2) in a separate post-run transaction, materialize and persist the reply Message via `ConversationBus.send()`. Never holds a transaction across provider execution. |
| **D14** | **Dual provenance verification & crash recovery** | `deliver_and_reply()` verifies both: (1) `run.agent == reply.sender` for authorship, and (2) the existing `MESSAGE_DELIVERED(parent_message, run)` marker for causal provenance. Crash recovery: if Relay crashed after run completion (`Run(SUCCEEDED)` + `run_output` committed) but before reply insertion, `deliver_and_reply()` recovers the reply from the durable `run_output` artifact, reconstructs a minimal successful `AgentResponse(output=content, agent=run.agent, role=...)`, and returns `AskOutcome(run=run, response=recovered_response)` without re-invoking the agent. Repeated calls return the existing reply idempotently. |
| **D15** | **Reply type specification** | `deliver_and_reply(message_id, reply_type=None)` accepts an explicit `reply_type`. If omitted, default inference is permitted *only* for the canonical pair (`CLARIFICATION_REQUEST -> CLARIFICATION_RESPONSE`). For other types, explicit `reply_type` is required; Relay never runs heuristic LLM classification over raw outputs to guess a type. |
| **D16** | **Authority boundary (D.8 invariant)** | P4.3 machinery may author only `Message` rows, `MESSAGE_SENT` markers, and delivery runs/events. It is structurally and behaviorally prohibited from mutating `TaskState`, `EvidenceRecord`, `Approval`, `Decision`, or `RelayConfig`. |

## 3. Migration Review: Foreign Key Analysis

### Decision: Trade-Off Analysis on SQLite Foreign Key on `reply_to_id`
`ALTER TABLE messages ADD COLUMN reply_to_id TEXT` will **not** declare `REFERENCES messages(id)`.

**Trade-Off Analysis:**
* **Pros of adding `REFERENCES messages(id)`:** Enforces referential integrity at the database engine level if records are inserted via raw SQL outside the application.
* **Trade-offs / Cons:**
  1. **SQLite `ALTER TABLE` Limitations:** In SQLite, adding a column with a `REFERENCES` clause via `ALTER TABLE ADD COLUMN` has known inconsistencies across SQLite versions when `PRAGMA foreign_keys = ON`.
  2. **Architectural Precedent:** In P4.2 (`Message.run_id`), Relay adopted the design trade-off of omitting the foreign key constraint on additive columns (`p4.2-role-resolution-delivery-plan.md` D2), relying instead on boundary-level validation.
  3. **Boundary Validation & Immutability:** The `ConversationBus` write path strictly verifies that `store.load_model(Message, reply_to_id)` exists prior to insert. Because `messages` has database triggers preventing `DELETE` and `UPDATE`, an existing parent can never be deleted out from underneath a child.
* **Conclusion:** The trade-off is resolved in favor of consistency with existing P4.2 schema migrations and reliable in-place upgrades.

## 4. Architectural Flows & State Transitions

### A. Two-Phase Delivery & Idempotent Reply Materialization

```text
deliver_and_reply(message_id, reply_type)
  │
  ├── 1. Check existing delivery markers: deliveries_for_message(message_id)
  │     ├── Existing delivery found:
  │     │     Load Run from marker reference (run:<id>)
  │     │     Verify MESSAGE_DELIVERED causal provenance binding
  │     │     ├── Run SUCCEEDED:
  │     │     │     Check existing reply: replies_for(message_id) matching run_id
  │     │     │     ├── Reply exists ──► Reconstruct AgentResponse(output=artifact.content)
  │     │     │     │                    RETURN existing reply idempotently (Zero Delta)
  │     │     │     └── Reply missing (Crash Window) ──►
  │     │     │           Load run_output artifact
  │     │     │           Verify run.agent == reply.sender
  │     │     │           Materialize Message via bus.send()
  │     │     │           Reconstruct AgentResponse(output=artifact.content)
  │     │     │           RETURN recovered AskOutcome + reply
  │     │     └── Run FAILED / RUNNING:
  │     │           RETURN DeliveryReplyOutcome(message, ask, reply=None)
  │     │
  │     └── No delivery found:
  │           Proceed to fresh execution
  │
  ├── 2. Fresh Delivery (P4.2 Pipeline):
  │     Tx1: Run(RUNNING) + run_input + AGENT_RUN_STARTED + MESSAGE_DELIVERED ──► COMMIT
  │     Provider / Harness Execution (NO TX HELD)
  │     Final Tx: Run(SUCCEEDED/FAILED) + run_output + AGENT_RUN_FINISHED ──► COMMIT
  │
  └── 3. Post-Run Reply Persistence:
        If Run SUCCEEDED:
            Verify run.agent == reply.sender
            Post-Run Tx: Message(reply_to_id, run_id) + MESSAGE_SENT ──► COMMIT
            Enforced by idx_messages_unique_reply_run (DB Uniqueness Constraint)
            RETURN DeliveryReplyOutcome(message, ask, reply)
        If Run FAILED:
            RETURN DeliveryReplyOutcome(message, ask, reply=None)
```

### Core Conversation Bus (`relay.core.bus`)

#### [MODIFY] `relay/core/bus.py`
* Define errors:
  ```python
  class ReplyRejected(MessageRejected):
      """Base error for reply linkage and pairing rejections."""

  class ReplyScopeMismatch(ReplyRejected):
      """Reply room_id or task_id does not match parent."""

  class ReplySymmetryViolation(ReplyRejected):
      """Reply sender/recipient does not match parent conversational direction."""

  class RoundTripLimitExceeded(ReplyRejected):
      """Reply exceeds the protocol-independent hard thread depth ceiling."""
  ```
* Constants:
  ```python
  DEFAULT_MAX_THREAD_DEPTH = 10
  ```
* Recipient Validation:
  Allow bare logical agents, `human:*`, and `relay:*`. Direct self-send (`sender == recipient`) rejected *only* for bare logical-agent identities (`if ":" not in message.sender and message.recipient == message.sender`).
* Reply Validation (`_validate_reply`):
  1. Load parent: `parent = store.load_model(Message, message.reply_to_id)`. If missing -> `ReplyRejected`.
  2. Scope equality: `message.room_id == parent.room_id` and `message.task_id == parent.task_id`.
  3. Addressing symmetry: `message.recipient == parent.sender` and `message.sender == parent.recipient` (direct) or parent's resolved recipient (role-addressed).
  4. Write-path cycle-safe thread depth calculation:
     ```python
     def _calculate_thread_depth(self, parent: Message, max_traversal: int = DEFAULT_MAX_THREAD_DEPTH + 1) -> int:
         seen = {parent.id}
         depth = 1
         current = parent
         while current.reply_to_id is not None:
             if current.reply_to_id in seen:
                 raise ReplyRejected(f"corrupt/cyclic reply ancestry detected at message '{current.reply_to_id}'")
             seen.add(current.reply_to_id)
             ancestor = self._store.load_model(Message, current.reply_to_id)
             if ancestor is None:
                 raise ReplyRejected(f"broken ancestry: parent '{current.reply_to_id}' not found")
             depth += 1
             if depth > max_traversal:
                 break
             current = ancestor
         return depth
     ```
     If `depth > max_thread_depth` -> `RoundTripLimitExceeded`.
* Query API:
  ```python
  def replies_for(self, message_id: str) -> list[Message]:
      """Direct children of message_id ordered chronologically using indexed lookup."""
      return list(self._store.all_models(
          Message,
          "WHERE reply_to_id = ?",
          [message_id],
          order_by="created_at ASC, rowid ASC"
      ))

  def has_answering_reply(self, message_id: str) -> bool:
      """True iff message_id has a qualifying canonical answering reply (P4.3 canonical pair)."""
      parent = self._store.load_model(Message, message_id)
      if parent is None or parent.type is not MessageType.CLARIFICATION_REQUEST:
          return False
      clause = "WHERE reply_to_id = ? AND type = ?"
      return next(self._store.all_models(Message, clause, [message_id, MessageType.CLARIFICATION_RESPONSE.value], limit=1), None) is not None

  def unanswered_blocking_messages(self, room_id: str | None = None, task_id: str | None = None) -> list[Message]:
      """Blocking clarification requests in scope that lack an answering response."""
      ...

      """Root-to-leaf thread leading to message_id, with cycle and depth guards."""
  ```

### Core Delivery Pipeline (`relay.core.delivery`)

#### [MODIFY] `relay/core/delivery.py`
* Define `DeliveryReplyOutcome`:
  ```python
  @dataclass(frozen=True)
  class DeliveryReplyOutcome:
      message: Message
      ask: AskOutcome
      reply: Message | None = None
  ```
* Add `deliver_and_reply()` to `MessageDelivery`:
  1. Load message. If missing -> `DeliveryRefusal`.
  2. Verify recipient is bare agent. If `human:*` or `relay:*` -> `DeliveryRefusal`.
  3. Resolve existing delivery: `deliveries = self.deliveries_for_message(message_id)`.
     - If delivery marker exists:
       - Extract `run_id` from marker references. Verify causal binding `MESSAGE_DELIVERED(message, run)`.
       - Load `run = self._store.load_model(Run, run_id)`.
       - If `run.status == RunStatus.SUCCEEDED`:
         - Load `run_output` artifact.
         - Reconstruct `recovered_response = AgentResponse(agent=run.agent, role=self._role_for(message), output=artifact.content)`.
         - Reconstruct `ask = AskOutcome(run=run, response=recovered_response)`.
         - Check existing reply: `existing = [m for m in self._bus.replies_for(message_id) if m.run_id == run.id]`.
         - If `existing`: return `DeliveryReplyOutcome(message=message, ask=ask, reply=existing[0])` (Idempotent Return).
         - If no reply: verify `run.agent == message.recipient`. Materialize reply from `artifact.content` via `bus.send(reply)`. Return `DeliveryReplyOutcome(message=message, ask=ask, reply=saved_reply)`.
       - If `run.status != RunStatus.SUCCEEDED`:
         - Return `DeliveryReplyOutcome(message=message, ask=AskOutcome(run=run), reply=None)`.
     - If no delivery marker exists:
       - Invoke `outcome = await self.deliver(message_id)`.
       - If `outcome.ask.response is None`: return `DeliveryReplyOutcome(message=message, ask=outcome.ask, reply=None)`.
       - Verify `outcome.ask.run.agent == message.recipient`.
       - Materialize reply from `outcome.ask.response.output` via `bus.send(reply)`.
       - Return `DeliveryReplyOutcome(message=message, ask=outcome.ask, reply=saved_reply)`.

## 8. Adversarial Consistency Audit

* **Against P4.1 Bus Invariants:**
  - Immutability: `messages` remains append-only. Replying inserts a NEW row; parent is never updated.
  - Senders: Bare senders still require proven `run_id`.
  - Self-send: Reject self-send for bare logical-agent identities only (`if ":" not in message.sender and message.recipient == message.sender`).
  - System Reservation: `MessageType.SYSTEM` remains reserved for `relay:*` senders.
* **Against P4.2 Delivery Invariants:**
  - At-most-once delivery initiation: Unchanged. `MESSAGE_DELIVERED` committed in Tx1.
  - Delivery grant: Harness recipients still downgraded to `READ_ONLY_ACCESS`.
  - Registry isolation: Core still consumes agents strictly via `AgentFactory` protocol.
  - Causal Provenance: Materialized reply verified against both `run.agent == reply.sender` and `MESSAGE_DELIVERED` marker.
* **Against SPEC Appendix D:**
  - D.4: Conversation is not state. Reply persistence does not mutate canonical task state or decisions.
  - D.6: No new `TaskState` introduced for blocking waits.
  - D.8: No hidden authority transfer through reply exchanges.
