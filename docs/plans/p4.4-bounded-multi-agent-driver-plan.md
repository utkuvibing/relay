## 0. Scope

**In:** `relay/core/driver.py` — a bounded, deterministic multi-agent driver
that chains Relay-mediated deliveries into a multi-hop conversation: typed
`ParticipantAddress` + `ConversationSpec` (with caller-stable
`conversation_key`) validated fail-closed zero-delta; **deterministic driver
Message identity** (frozen JSON canonical vector → UUIDv5 Message ids) with
create-or-reuse on the `messages.id` PRIMARY KEY, semantic-equality
verification, and IntegrityError disambiguation; per-hop `deliver_and_reply`
with **explicit** reply_type (no inference); verbatim hub forwarding
(`relay:driver`-authored); bounded new-Message retry on failed hops; RUNNING
deliveries treated as **crash-safe pending re-entry**; `resume(seed_message_id)`
delivering the seed as hop 1 with deterministic key verification (driver-owned:
re-derivation; foreign: `foreign:<seed.id>`); `ConversationResult` with stop
reason; exit-gate integration proof (api → harness → different harness, and
A→B→A, over fakes, one driver call, zero human steps) including the G6
concurrency/identity matrix; authority-boundary AST test extended to
`driver.py`; skip-by-default live smoke; README P4 row → Done.

**Out (explicit):** communication policy, permission matrices, per-pair
purposes, budgets, protocol semantics, early-stop-on-answered (P5); stage
pausing/resumption on blocking clarification — D.11's "blocking pauses the
stage" is P6's consumption of the communication-level state P4.4 exposes (D.6:
no new TaskState); D.10 context reconstruction / transcript assembly (P7);
persistent Rooms/seats, `@role` chat syntax (P7); CLI surfaces (`relay
discuss` is P5/P7); schema changes of any kind — v5 stands, identity is
client-derived (D13); new EventTypes; same-message redelivery override
mechanics (P4.2 D13 stays unconditional; retries are new Messages only);
dead-letter queues; reply-type heuristics of any kind; string prefix role
encoding in driver addressing; content-addressed identity hashing;
UUID-version-based ownership inference.

## 1. Code audit — facts this builds on (verified against merged `e08fea5` content)

* `ConversationBus.send()` is the single write path; role resolution
  pre-persistence; strict authorship (bare sender ⇔ `run_id` validated against
  `run.agent == sender`; `relay:*`/`human:*` senders must NOT carry `run_id`);
  content cap 50k typed-rejected at send; `MessageType.SYSTEM` reserved for
  `relay:*` (one-directional — `relay:driver` may send non-SYSTEM types);
  self-send denial exempts prefix senders.
* **`Message.id` is caller-settable** (`models.py:152`):
  `id: str = Field(default_factory=new_id)` with `new_id = uuid.uuid4().hex`
  (`models.py:26`). A driver-composed Message carrying an explicit id
  persists as-is; store-generated ids are uuid4-hex. Driver ids are
  `uuid.uuid5(<namespace>, canonical).hex` — process/platform-stable.
  **Ownership is NEVER inferred from id shape or UUID version (rev 4)** —
  `Message.id` is arbitrary caller data; ownership is
  `sender == DRIVER_SENDER` plus successful re-derivation (D14).
* **PK-conflict create-or-reuse is available with no schema change**
  (`store.py:221-227`, `bus.py:138-143`): `save_model` performs a plain
  `INSERT INTO messages (...)`; `messages.id` is the PRIMARY KEY; a duplicate
  id raises `sqlite3.IntegrityError` inside `bus.send`'s
  `with self._store.transaction():` block — the transaction rolls back
  atomically (no Message row, no MESSAGE_SENT marker) and the error
  propagates to the caller. `bus.send` may also raise IntegrityError for
  unrelated constraint reasons — D13's handler disambiguates by reloading the
  expected id and re-raising when the row is absent.
* **Role provenance is persisted on Message rows** (`models.py:144-146`):
  "`recipient_role` preserves the original role address when the sender
  addressed a role". Role-addressed sends set `recipient_role` with
  `recipient=None` (`bus.py:163-171` — the bus rejects pre-filled recipients
  and resolves itself); the persisted row then carries `recipient` = resolved
  agent + `recipient_role` = role. Direct sends persist `recipient_role =
  None`. **Consequence: direct `agent=claude` and role-addressed
  `reviewer→claude` produce rows that differ in `recipient_role` (NULL-strict)
  even when `recipient` matches** — the distinction D13's canonical identity
  freezes.
* **Reply-type inference is narrow** (`delivery.py:371-380`,
  P4.3 plan D15): `deliver_and_reply(..., reply_type=None)` infers ONLY
  `CLARIFICATION_REQUEST -> CLARIFICATION_RESPONSE`; any other parent type
  raises `InvalidReplyTypeRefusal`. **Every driver call therefore passes
  `reply_type` explicitly** (D12).
* **Materialized replies** (`delivery.py:383-401`): sender = parent.recipient,
  recipient = parent.sender, `reply_to_id` = parent.id, `run_id` = delivery
  run, scope inherited exactly, `type` = resolved reply_type, content = run
  output, `blocking=False` always, references empty.
* **Reply validation is structural only** (P4.3 D9): parent existence, exact
  scope equality, sender/recipient symmetry, cycle-safe depth ≤
  `DEFAULT_MAX_THREAD_DEPTH = 10`. **Consequence (load-bearing): a forward to
  agent B cannot be a structural reply to A's answer** — symmetry would force
  it back to A. Forwards are fresh top-level messages; the answer travels via
  content (verbatim) + `references` (provenance through `context_refs`
  pass-through, P4.2 D15). **Downstream driver messages are therefore NOT
  `reply_to_id`-chained — reply-chain traversal is not a valid identity or
  verification mechanism (rev 4).**
* **`references` are generic non-empty strings** (`bus.py:220-222`) —
  `message:` and `run:` refs are both legal on Message rows (P4.2 D1 already
  sanctions run citations by prefix senders). Retry forwards cite the failed
  attempt's message and run.
* `MessageDelivery.deliver_and_reply(message_id, *, reply_type=None,
  max_thread_depth=DEFAULT_MAX_THREAD_DEPTH) -> DeliveryReplyOutcome(message,
  ask, reply)` — at-most-once initiation, Tx1 binding marker, preflight
  reply-type/thread-depth validation before provider I/O, harness recipients
  always READ_ONLY (P4.2 D8, no fallback), recovery: SUCCEEDED →
  materialize/recover reply idempotently (the partial unique index
  `idx_messages_unique_reply_run` makes one reply per (parent, run)
  database-guaranteed); FAILED → preserved sanitized error, no reply;
  RUNNING → typed `DeliveryPendingRefusal`, zero delta. **Re-entry on an
  already-delivered message never re-invokes the agent — this is what makes
  hop-1 processing of an already-delivered seed safe (rev 4).**
* `MessageDelivery.deliveries_for_message(message_id)` — read-only
  observability helper (P4.2 D13); **demoted to diagnostics in rev 3/4** — the
  deterministic ID is the authoritative idempotence primitive.
* Messages append-only (Python `_APPEND_ONLY_TABLES` + SQLite triggers); no
  new EventType needed — the feed composes events generically and every driver
  action is a Message, Run, or existing marker.
* `RoleResolver` Protocol (`resolve_role`, `knows_agent`) — the same seam the
  bus uses; `ConfigRoleResolver` + `roles:` config is production-backed. Core
  stays registry-free: the driver consumes agents only through
  `MessageDelivery`/`AgentFactory` (AST-tested).
* Suite baseline after P4.3 merge: 575 passed / 9 skipped, ruff clean.

## 2. Frozen decisions

| # | Decision |
|---|---|
| D1 | **Hub topology (user-frozen, rev 1):** the driver authors messages as `sender="relay:driver"` (module constant `DRIVER_SENDER`), never carrying `run_id` (P4.2 D1). Agent-authored traffic exists only as P4.3-materialized replies (`sender = run.agent`, `reply_to_id` set, recipient = parent sender). The driver never fabricates agent authorship; it is visible in the ledger as the mediator. Chain-style agent-authored forwarding (sender=A addressed to B) is rejected: it would misrepresent driver-composed content as A's addressed speech. |
| D2 | **Forward shape (frozen rev 3):** each normal forward is a fresh top-level Message (`reply_to_id=None`), `recipient` = the resolved next participant (direct: `recipient=<agent>`; role: `recipient_role=<role>`, `recipient=None` — the bus resolves), `content` = the previous answer's content **verbatim** (replies are ≤50k by bus cap, so forwards always pass the cap — no truncation path exists), `type = note`, `blocking = False`, and **exactly one reference: `[f"message:{answer.id}"]`**. **Exception — retry forwards** cite the failed attempt instead: `[f"message:{failed.id}", f"run:{failed.run_id}"]` — normal forwards carry one `message:` ref, retry forwards `message:` + `run:` refs; the split is structural, never mixed. Forward phrasing/template is an implementation detail; the field set and the normal/retry reference split are frozen. |
| D3 | **ConversationSpec (frozen rev 3):** frozen dataclass with `conversation_key: str` (REQUIRED — D13/D14), `room_id: str` (required — traffic scoping is the driver's concern, discharging the P4.2 open item), `task_id: str \| None`, `participants: tuple[ParticipantAddress, ...]` (hop order), `seed_content: str \| None`, `seed_type: MessageType = NOTE`, `seed_blocking: bool = False`. **`ParticipantAddress` is a frozen dataclass with exactly one of `agent: str` (direct logical agent) or `role: AgentRole` (role address) set** — never both, never neither; the role arm speaks the `AgentRole` enum, NOT a string with prefix encoding, per frozen P4.2 D5; exactly-one-of is enforced at spec validation (D4), not by string inspection. **Bounds frozen:** `1 <= len(participants) <= MAX_SPEC_PARTICIPANTS = 8` and `MAX_HOP_RETRIES = 1` — code constants, no config surface. **Start-only seed fields (frozen rev 3):** `seed_content`, `seed_type`, `seed_blocking` are START-ONLY. `start()` requires non-empty `seed_content`; `resume()` requires `seed_content` unset and `seed_type`/`seed_blocking` at their defaults — any deviation is a typed `SpecRefusal`. On resume the persisted seed is authoritative for type, blocking, and content (D14). |
| D4 | **Spec validation is fail-closed pre-persistence (AMENDED rev 4):** before any Message exists the driver validates, all-zero-delta, typed `SpecRefusal` on violation: `conversation_key` present, non-empty after strip, ≤ 256 characters, **and MUST NOT begin with the reserved `foreign:` prefix in `start()` specs** (the foreign-seed canonical-key namespace, D14); every `ParticipantAddress` is exactly-one-of; each direct agent passes the injected `RoleResolver.knows_agent`; each role address resolves via `RoleResolver.resolve_role` (unresolved → refusal); participant count within `[1, MAX_SPEC_PARTICIPANTS]`; `room_id` non-empty; start-only seed-field rules per D3. Routing speaks only logical identity/role — the driver contains no backend-family/provider conditionals (C.7; proven by AST scan in G4). Heterogeneity is invisible to the driver: it rides the family-blind delivery spine. |
| D5 | **Round mechanics (AMENDED rev 4 — resume hop semantics):** one hop = (deterministic identity per D13) → compose the message via `bus.send` (create-or-reuse) → `delivery.deliver_and_reply(message.id, reply_type=<per D12>)`. The materialized reply (sender=agent, `run_id` set, `reply_to_id` = the message's id, `blocking=False`) is the hop's answer. Message kinds: **`seed`** (hop 1, driver-composed by `start()`), **`forward`** (hop i ≥ 2), **`retry`** (any hop's attempt-2 message after a failed attempt). `DriverHop.forward` carries the TERMINAL attempt message (the seed for an unretried hop 1). **`resume()` processes the persisted seed as hop 1 through `deliver_and_reply(seed.id)` — it never skips to participant 2.** An already-delivered seed → P4.3 recovery/idempotence returns the existing reply without re-invocation; a never-delivered seed → participant 1 runs for the first time. Only after the hop-1 answer is obtained/recovered may the driver create the hop-2 forward (D13 identity). `start(spec)` composes the seed (`relay:driver`, spec scope, spec type/blocking, no run_id) and traverses all participants from hop 1 identically — start and resume differ only in seed provenance/composition, never in traversal. |
| D6 | **Retry policy (user-frozen rev 1; AMENDED rev 3):** a hop whose delivery run FAILED is retried at most `MAX_HOP_RETRIES = 1` times by composing a **new** Message (kind `retry`, attempt index 2) whose `references` cite the failed attempt (`message:<failed.id>` + `run:<failed.run_id>`, D2 exception); at-most-once initiation (P4.2 D13) is untouched — no same-message re-initiation mechanism exists or is added. The retry message's identity is the D13 derivation at attempt index 2 with `prev` = the failed message's id — **stable across crash/re-entry**, so a crash between retry-creation and its delivery reuses the existing retry row on re-entry instead of duplicating it. **RUNNING deliveries are crash-safe pending re-entry, not run recovery:** a `DeliveryPendingRefusal` stops the conversation with stop reason DELIVERY_PENDING — the driver does not wait, poll, or fabricate an outcome; a later `resume()` under the same `conversation_key` re-enters, and P4.3's recovery (SUCCEEDED → idempotent reply / FAILED → preserved error / still-RUNNING → pending again) resolves the state honestly. A second failure stops with HOP_FAILED. **AMENDED rev 4 pre-merge:** a failed `CLARIFICATION_REQUEST` hop is never retried as a NOTE — the retry's reply would be a NOTE, replacing the canonical `clarification_request → clarification_response` answering pair (P4.3 D10) and corrupting the unanswered semantics; the hop stops HOP_FAILED immediately and the blocking request stays honestly in `unanswered_blocking_messages`. Bounded new-Message retries stand for ordinary NOTE parents. |
| D7 | **Termination is structural (user-frozen, rev 1):** the driver stops when (a) the participant sequence is exhausted (SEQUENCE_EXHAUSTED), (b) a hop exhausts retries (HOP_FAILED), or (c) a hop is pending (DELIVERY_PENDING). No wait/poll loops, no scheduling — the driver is a bounded synchronous async traversal. **There is no unbounded loop**; the bounded traversal and bounded retry loop are the only cycles. P5 layers policy (early-stop on answered seeds, per-pair rules) on top later. |
| D8 | **Result model (frozen rev 2):** frozen `ConversationResult(seed: Message, hops: tuple[DriverHop, ...], stop_reason: StopReason, final_answer: Message \| None)` where `DriverHop(forward: Message, outcome: DeliveryReplyOutcome, attempts: int)` — `forward`/`outcome` describe the TERMINAL attempt (the message actually answered or finally failed), and `attempts` is the total attempt count (1 or 2). Intermediate failed messages remain in the ledger, cited by the retry message's references. Spec-validation refusals are typed exceptions (zero delta), not results. |
| D9 | **Recipient-side context policy (user-frozen, rev 1):** each participant receives exactly the P4.2 D15 envelope (sender/type/blocking/content) plus the single forwarded-answer ref via `context_refs` pass-through; adapter consumption remains adapter policy. No transcript assembly, no D.10 reconstruction (P7). |
| D10 | **No schema change, no new EventType (frozen rev 1; reinforced rev 3/4):** schema v5 stands. Driver message identity is CLIENT-DERIVED (`uuid5` over a frozen canonical string) and rides the existing `messages.id` PRIMARY KEY — no migration, no table, no index, no EventType. Feed needs zero changes. |
| D11 | **Authority boundary (D.8; user-frozen, rev 1):** the driver may author only Message rows (via the bus) and cause delivery Runs/events (via delivery). TaskState, EvidenceRecord, Approval, Decision, policy stay byte-identical — proven behaviorally including the exit-gate chain. AST import-direction boundary extended to `driver.py` (no `relay.agents.registry`, no `state_machine`/`evidence`/`permissions` direct imports). |
| D12 | **Explicit reply_type discipline (frozen rev 2 — no inference):** every `deliver_and_reply` call from the driver passes `reply_type` explicitly. The driver computes it from the parent message's persisted type: parent `CLARIFICATION_REQUEST` → `MessageType.CLARIFICATION_RESPONSE`; **every other parent type (NOTE messages and all non-clarification seeds) → `MessageType.NOTE`**. The driver's reply-type vocabulary is exactly `{CLARIFICATION_RESPONSE, NOTE}` — no heuristic inference, no content classification, and P4.3's default-inference path is never relied upon (it would raise `InvalidReplyTypeRefusal` on NOTE parents). |
| D13 | **Deterministic driver message identity (REWRITTEN rev 4 — supersedes the rev-2 lookup contract and rev-3's `\x1f` serialization):** every driver-authored Message (kinds `seed`, `forward`, `retry`) carries a **deterministic id derived from canonical identity data — never from message content**. **Canonical serialization (collision-safe):** a UTF-8 **JSON array** in this fixed field order — `[version, conversation_key, room_id, task_id, hop_index, attempt_index, kind, prev_message_id, recipient_role, resolved_recipient]` — with `version = "relay.driver.identity.v1"` and **real JSON `null` for absent nullable values (no `"-"` sentinel)**, serialized with frozen settings (`json.dumps(..., ensure_ascii=True, separators=(",", ":"))` — byte-stable, locale/platform-independent); the id is `uuid.uuid5(<frozen module namespace UUID constant>, canonical_string).hex`. **Same logical driver message always derives the same id** (UUIDv5/SHA-1, platform- and process-stable). JSON encoding is injective over the fixed-shape vector: separator characters, literal `"-"`, Unicode, and nulls cannot alias distinct identity tuples (G6 13). **Role provenance (rev 3):** the canonical participant identity includes BOTH `resolved_recipient` AND `recipient_role` with NULL-strict semantics — direct `agent=claude, role=None` and role-addressed `resolved=claude, role=reviewer` derive different ids and are never interchangeable. **Create-or-reuse contract (AMENDED rev 4 — disambiguated):** derive the expected id → compose the Message with it → `bus.send`; on `sqlite3.IntegrityError` (the transaction has already rolled back atomically): **reload the existing row by the derived id and verify exact semantic equality** — sender, recipient, recipient_role (NULL-strict), type, blocking, content (byte-equal), references (exact ordered list equality), scope (room_id equal, task_id NULL-strict), `reply_to_id` (both None for driver messages). **Exact match → reuse it** (proceed to `deliver_and_reply`; P4.3 recovery makes re-delivery idempotent). **Any mismatch → typed `DriverIdentityRefusal`** (corruption/identity collision), zero further persistence. **Row absent → re-raise the original IntegrityError** — an unrelated database constraint failure is never reinterpreted as an idempotent race. Content is deliberately NOT a hash input: two compositions with the same identity inputs but different content collide on the derived id and are caught by the equality verification as a corruption refusal, never silently absorbed. **Conversation identity:** `conversation_key` is the caller-stable name of one logical driver conversation — the same key under the same canonical inputs re-derives the same ids (crash/re-entry recovery, G6 1/3/4/7); a different key derives different ids even when scope, participants, and content are identical (distinct conversations, G6 2). `deliveries_for_message` and bus queries remain available for diagnostics only; the deterministic id is the authoritative idempotence primitive. |
| D14 | **`resume()` seed validation, ownership, and key verification (REWRITTEN rev 4):** before traversal, all checks pre-persistence with typed refusals and zero store delta: (1) the seed Message exists (`ResumeSeedRefusal`); (2) its scope matches the spec scope exactly (`room_id` and `task_id`, NULL-strict); (3) `participants` is non-empty (D3); (4) `seed.recipient` is a deliverable bare logical agent — no `human:`/`relay:` prefix (mirroring the delivery refusal boundary, P4.3 D8); (5) `seed.recipient` equals the resolved first participant (direct agent → identity; role → `resolve_role` result); (6) start-only spec fields are at defaults (D3); (7) **ownership + key verification — NEVER by UUID shape/version (rev 4):** **driver-owned = `seed.sender == DRIVER_SENDER`** → re-derive the expected seed id under the presented `conversation_key` from the persisted seed's canonical fields (kind `seed`, hop 1, attempt 1, `prev=null`, participant/scope fields from the row): **re-derivation succeeds → proceed; fails → `ConversationKeyMismatchRefusal`** (the seed belongs to a different conversation). **foreign = `seed.sender != DRIVER_SENDER`** → the conversation key is canonical, derived from the immutable seed identity: **`foreign:<seed.id>`**; `spec.conversation_key` MUST equal it exactly — **mismatch → `ConversationKeyMismatchRefusal`** (zero persistence, zero agent invocation). The canonical foreign key makes foreign-seed identity deterministic with zero added state: the same foreign seed cannot be resumed into two parallel driver conversations. (8) The seed is the immutable root: resume never rewrites, re-addresses, or re-authors it (append-only storage makes this structural; resume only reads it and delivers it). (9) **Traversal begins at hop 1 (D5):** `deliver_and_reply(seed.id)` first; the hop-2 forward is created only after the hop-1 answer is obtained/recovered. Any mismatch → typed refusal, zero persistence, zero agent invocations. |

## 4. Acceptance gates

* **G1 Spec validation:** unknown agent / unresolved role / both-or-neither
  `ParticipantAddress` arms / empty or oversize participant list / missing
  room / empty, oversize, or `foreign:`-prefixed `conversation_key` on
  `start()` / `start()` without seed content / `resume()` with any start-only
  field set → typed `SpecRefusal`, store byte-identical (zero delta), before
  any Message exists.
* **G2 Hub mechanics:** per-hop ledger shape exact — driver messages:
  `relay:driver`, no `run_id`, `reply_to_id=None`, scope = spec scope, refs
  per D2 (normal: exactly `message:<answer>`; retry: `message:<failed>` +
  `run:<run>`), **ids match the D13 derivation recomputed from each row's
  observable canonical fields**; reply: agent sender with `run_id`,
  `reply_to_id` = the driver message's id, recipient `relay:driver`,
  `blocking=False`; forward content equals the answer content byte-for-byte;
  **reply_type discipline: forward replies persist as NOTE, clarification
  seeds produce CLARIFICATION_RESPONSE replies, and a pinned test proves
  `reply_type=None` on a NOTE parent raises `InvalidReplyTypeRefusal` (the
  no-inference contract)**; harness hops bind READ_ONLY instances (asserted on
  the profile the run actually used); seed types/blocks pass through bus
  validation (blocking on non-eligible type → bus rejection surfaces).
* **G3 Boundedness + idempotence:** sequence exhaustion stops
  deterministically; FAILED hop → exactly one new-Message retry (refs cite the
  failed attempt), second failure → HOP_FAILED with exact store deltas and
  `DriverHop.attempts == 2` with terminal-attempt semantics; RUNNING →
  DELIVERY_PENDING (crash-safe pending re-entry: no retry, no re-invocation; a
  later same-key `resume()` re-enters honestly); **full-chain
  idempotence: re-running `start()` or `resume()` after each crash window —
  post-create/pre-delivery, post-delivery-initiation (RUNNING), post-run/
  pre-reply, post-forward-create/pre-delivery, post-retry-forward-create —
  yields zero duplicate rows and an identical result**; `resume()` validation
  matrix (D14) refuses with zero persistence; **no unbounded loop exists** —
  the bounded traversal and bounded retry loop are the only cycles.
* **G4 Exit gate:** api→harness→different-harness and A→B→A chains complete
  in a single driver call with zero human steps; all traffic in one scope;
  routing decisions reference only names/roles (AST scan of `driver.py` finds
  no family/provider strings or conditionals); canonical state
  (TaskState/Evidence/Approval/Decision) byte-identical across the whole
  chain.
* **G5 Architecture:** AST boundary extended to `driver.py`; no schema
  migration (fresh DB lands at v5 unchanged); full suite green; ruff clean.
* **G6 Identity & concurrency (mandatory matrix, all fourteen):**
  1. Same scope/content/participants + same `conversation_key` → idempotent
     reuse (same derived ids, no duplicate rows, converging result).
  2. Same scope/content/participants + different `conversation_key` →
     distinct conversations (different derived ids, independent rows).
  3. Concurrent `start()` with the same `conversation_key` (threaded,
     barrier-synchronized, independent connections) → exactly one
     deterministic seed row; losers reuse via PK-conflict reload with equality
     verification.
  4. Concurrent downstream forward creation → exactly one deterministic
     forward row (same race pattern).
  5. Direct `agent=claude` and role-addressed `role=reviewer → claude` →
     distinct canonical driver identities and distinct Message rows
     (NULL-strict `recipient_role` in both the derivation and the equality
     check).
  6. A pre-existing row at the derived id with different content/addressing/
     scope/references/type → typed `DriverIdentityRefusal`, zero further
     persistence.
  7. Retry-forward deterministic identity stable across crash/re-entry: the
     attempt-2 row re-derives identically after a crash between its creation
     and delivery, and is reused, not duplicated.
  8. Driver-owned resume: correct key re-derivation succeeds and converges
     (idempotent, zero-delta re-entry); wrong key →
     `ConversationKeyMismatchRefusal` zero-delta.
  9. **Fresh foreign-seed resume: hop 1 executes participant 1 for the first
     time; key `foreign:<seed.id>` accepted.**
  10. **Already-delivered foreign-seed resume: hop 1 recovered via P4.3
      idempotence without re-invocation, then hop 2 proceeds.**
  11. **Wrong foreign-seed key → `ConversationKeyMismatchRefusal`, zero
      delta, zero invocation.**
  12. **UUID shape/version never determines ownership** (a v5-shaped id on a
      foreign sender is foreign; a store-shaped id claiming the driver
      sender is refused when re-derivation fails — shape alone neither
      grants nor denies ownership).
  13. **Canonical serialization collision tests: separator characters, literal
      `"-"`, Unicode, and JSON null cannot alias distinct identity tuples.**
  14. **Unrelated `IntegrityError` with no row at the expected deterministic
      id → re-raised, never reinterpreted as an idempotent race.**
