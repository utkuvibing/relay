## 1. Accepted scope and boundaries

Implement standalone YAML protocol/stage definitions, strict validation,
stage-scoped accounting, message-type schedules, typed ledger facts, pure
completion evaluators, and one debate example. Reuse the existing P5.1 bus,
delivery, policy, and transactional accounting boundaries.

No multi-stage runner, automatic progression, participant capability binding,
context aggregation, definition pinning, or repetition execution (P5.3). No
`relay discuss`, escalation UX/records, or refusal rendering (P5.4). No
canonical task, evidence, approval, or decision mutations. The P4 driver and
its frozen message identity remain unchanged.

## 2. Definitions and interfaces

`relay/core/protocols.py` owns frozen validated dataclasses. Tuple fields
prevent mutable nested collections. Unknown fields and invalid vocabulary are
rejected for both YAML and programmatic construction.

| Interface | Contract |
| --- | --- |
| `ProtocolDefinition` | String name/version, participant requirements, finite ordered stages, protocol completion rules. |
| `ParticipantRequirement` | Existing `AgentRole` and existing required-capability vocabulary, never provider/model selectors. |
| `StageDefinition` | Unique ID, participating roles, explicit edges, allowed types, budgets, expected outputs, completion rules. |
| `StageEdge` | Exact role pair, tuple of allowed types, explicit blocking permission; converted to P5.1 `PolicyEdge`. |
| `StageBudgets` | Strict integer turn/blocking limits with P5.1 ranges, converted to `CommunicationBudgets`. |
| `ExpectedOutput` | Exactly one declared output type per participating role. |
| `StageCompletion` | `require_synthesis=False`, `early_stop_on_answered=False`. |
| `ProtocolCompletion` | `require_synthesis=False`. |
| `StageContext` | Protocol name/version, execution key, stage ID, nonnegative occurrence index, nullable exact room/task scope. |
| `load_protocol(path)` | Explicit-path standalone YAML loading; typed `ProtocolLoadError`, including field locations or duplicate-key source position. |

The loader is in `relay/context/protocols.py`. It uses existing PyYAML and
Pydantic dependencies, with duplicate-key rejection. No file discovery or
`relay.yaml` changes are introduced. YAML versions must be strings, e.g. `"1"`.

Validation rejects empty/duplicate participants or stages, undeclared roles,
unknown capabilities/message types, missing edges, duplicate/self edges,
invalid blocking edges/budgets, and types outside the stage schedule.
`system` is never a stage message type. An explicitly empty edge tuple denies
all agent-to-agent pairs. Synthesis requirements need a declared synthesis
output. Stages do not branch, repeat, or execute `max_rounds`.

## 3. Pure facts and completion boundary

All boundary records are frozen dataclasses with tuple collections:

| Record | Fields |
| --- | --- |
| `StageRequestFact` | Role; optional request ID; `missing/pending/failed/succeeded` state; optional reply ID/type. Success requires request and reply identifiers/type. Missing has no request ID. |
| `StageAnswerFact` | Blocking clarification seed ID; optional canonical answering-reply ID. |
| `BudgetExhaustionFact` | Typed `aggregate/stage` scope and `turn/blocking` dimension. |
| `StageFacts` | Context, derived stage key, request facts, answer facts, optional budget exhaustion. |
| `StageEvaluation` | Context/key, `continue/complete/blocked` status, typed reason, supporting message IDs, qualifying synthesis IDs. |
| `ProtocolEvaluation` | Status, typed reason, supporting message IDs, qualifying synthesis IDs. |

`evaluate_stage(definition, facts)` and `evaluate_protocol(definition,
stage_results)` perform no ledger, filesystem, clock, provider, or scheduling
I/O. They validate context/key, expected roles, duplicate identities, stage
order, and common execution/scope. Protocol evaluation accepts an ordered
prefix for incomplete progress; occurrence indexes must be zero because
repetition execution is deferred.

`relay/core/stage_facts.py` provides the separate read-only
`collect_stage_facts(store, definition, context, expected_request_ids,
clarification_seed_ids=(), *, policy=None, next_message_blocking=False)` boundary.
The request map names expected request IDs by role; absent roles produce
explicit missing facts. Supplied IDs must exist and match stage/scope and
role provenance. The collector validates unique delivery bindings, Run
identity/status, reply symmetry/type claims, and exact persisted output
content. Contradictory or foreign records raise `ProtocolFactsError`.

Collection uses one deferred read transaction, or reuses a caller-owned
transaction without closing it. It never materializes missing replies. A
succeeded Run awaiting reply persistence remains pending. When a policy gate
is supplied, budget observations use the same ledger snapshot; custom gates
must honor the read-only, same-ledger contract. Blocking exhaustion is queried
only when `next_message_blocking=True`: a zero blocking allowance does not
prevent a nonblocking stage from progressing.

Evaluators trust validated facts; persistence provenance belongs to the
collector, not the evaluator. They implement these rules in order:

1. Complete when all expected outputs have successful canonical replies of
   the declared types and any required synthesis is present.
2. Otherwise, early-stop only when enabled and an explicit nonempty set of
   blocking clarification seeds is entirely answered by canonical
   `clarification_response` replies. This cannot bypass required synthesis.
3. Otherwise, a failed request or budget exhaustion blocks completion.
4. Otherwise, continue awaiting output or required synthesis.

Completion wins over exhaustion after the last available turn succeeds.
Protocol completion requires all stages and any protocol synthesis requirement;
early-stopping one stage never skips another stage. Model prose claiming
completion, arbitrary messages, and other stages' messages are not evidence.

## 4. Frozen stage-key identity

The exact canonical identity vector is:

```python
[
    "relay.stage.identity.v1",
    protocol_name,
    protocol_version,
    execution_key,
    stage_id,
    occurrence_index,
    room_id,
    task_id,
]
```

Serialization and digest are exactly:

```python
canonical_bytes = json.dumps(
    identity_vector,
    ensure_ascii=True,
    separators=(",", ":"),
    allow_nan=False,
).encode("utf-8")

stage_key = "stage:v1:" + hashlib.sha256(canonical_bytes).hexdigest()
```

String identities must be nonempty and are preserved verbatim: no trimming,
case folding, or Unicode normalization. The occurrence index is a nonnegative
integer; booleans are invalid. Scope components are nonempty strings or
`None`, with at least one non-null component. `None` encodes as JSON `null`,
which is distinct from the string `"null"`; fixed array positions distinguish
room-only and task-only scope. Budgets, message content, and definition hashes
are excluded, so budget edits do not mint a new accounting key.

Two literal hash/byte golden vectors freeze the contract, plus nullable-scope,
Unicode, separators, invalid-input, and re-entry checks. Callers must reuse a
stable execution key and immutable protocol definition on resume. Durable
execution records and definition pinning remain P5.3.

## 5. Runtime integration and migration

Bus and delivery accept optional keyword-only `stage_context` and `protocol`.
Scoped services require the additive `StageCommunicationPolicyGate` interface;
the P5.1 unscoped gate method signatures remain unchanged. Delivery and its
bus must share context, definition, and policy gate.

`StageAdmission` centralizes stage validation in `relay/core/stage_policy.py`.
The bus stamps messages and sent markers. Delivery stamps delivery-binding
markers and replies. Unscoped services refuse stage-tagged traffic. Parent,
reply, binding, and active stage keys/scopes must agree; use semantic
references for cross-stage context rather than cross-stage reply linkage.

Stage schedules and declared roles apply to Relay-mediated conversational
traffic as well as agent messages. The Human/Relay pair exemption does not
bypass stage types. Agent pairs must satisfy both workspace and stage edges;
stages cannot widen workspace permissions.

Blocking admission remains in the bus transaction; delivery-turn admission
remains in Tx1 after the duplicate check. Both aggregate and stage limits
must admit fresh spending. Stage SQL uses exact nullable scope plus key;
aggregate SQL counts all traffic, including legacy rows. Failed runs spend a
turn; a fresh retry request needs another turn. Human blocking messages are
exempt; Relay and agent blocking messages count.

Previously admitted replies retain their exact type claim plus matching stage
identity across recovery and later policy/schedule changes. Recovery spends
no additional turn. Standalone delivery without a reply-type claim must
recheck current reply admission. Stage context/schedule refusals are typed;
budget refusals retain the existing hierarchy and expose scope/dimension.

Schema v6 adds nullable `stage_key` to messages and event log entries, plus
indexes for stage blocking and delivery counts. The generic model codec and
explicit event writer/decoder round-trip the fields. Historical rows stay
`NULL`; append-only triggers, event vocabulary, and P4 driver identities are
unchanged. Existing unscoped configuration and APIs retain P5.1 behavior.

## 7. Terminal-state correctness follow-up

`CANCELLED` is terminal and now maps to `RequestState.FAILED`, alongside
`FAILED`. Only `RUNNING` remains pending on the unsuccessful-Run path;
`SUCCEEDED` retains the canonical reply/provenance requirements. An unmet
cancelled required output produces `BLOCKED` / `REQUEST_FAILED`, including
when its consumed delivery turn exhausted the stage budget.

Six focused regression cases cover all four Run statuses, cancellation
recovery as a terminal refusal rather than pending progress, and rejection
of replies attached to unsuccessful terminal Runs. The cancelled case was
observed failing before the production fix; the other five cases passed.

The related RunStatus/RequestState, delivery recovery, fact collection,
completion, and budget paths were reviewed. No additional demonstrated P5.2
terminal-state defect required a production change; P4 delivery's existing
terminal refusal behavior and P5.2 completion-before-exhaustion precedence
remain intact. No new public RequestState was introduced.
