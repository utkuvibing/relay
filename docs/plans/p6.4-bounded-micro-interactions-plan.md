# P6.4 — Bounded micro-interactions inside build stages

Status: implemented.

## Accepted scope

SPEC §27 Phase-6 "bounded micro-interactions inside stages" (App. D.4–D.9,
D.11-P6): a one-shot stage run reaches another participant only by ending
its whole output with one strict `relay.stage_signal.v1` object. Relay
translates it into a task-scoped bus `Message` (`run_id` authorship,
`recipient_role`, blocking per kind), resolves blocking signals through the
existing `deliver_and_reply`, promotes `challenge`/`proposal` answers into
`Decision` records (and, on `accept` + `plan_effect: supersede`, a
superseding `PLAN` artifact + `relay.plan_revision.v1` link), and
re-dispatches the stage as a same-attempt continuation carrying the
exchange. All four exchange shapes:

- implement/fix → planner `clarification_request` (answer: `clarification_response`);
- implement/fix → planner `proposal` (answer: `final_position` carrying
  `relay.planner_decision.v1`);
- review → implementer `clarification_request`;
- review → planner `challenge` (answer: `final_position` decision);
- implement/fix `note` (non-blocking, best-effort) to planner/reviewer.

Reviewer `note` is deliberately excluded — reviewer output keeps the strict
`relay.review.v1` contract; any illegal kind/role is a stage-contract
violation, never a composite envelope.

Locked semantics: continuation runs repeat `build_attempt:N` with causal
marker refs and never consume `budget.max_fix_loops`; communication budgets
(`max_blocking_messages`, `max_agent_turns`) bound the micro-loop; signal
instructions are advertised only when the counterpart role resolves via
`roles:` AND policy admits the exact send + reply edges AND budgets have
headroom AND the resolved recipient differs from the emitter — otherwise
prompts stay byte-identical to pre-P6.4; every blocked exchange persists a
deduped `relay.build.escalation.v1` and parks; the human fixes
config/policy/budget and runs `relay continue`. No new `TaskState`; no
human-authored replies (P7+).

## Emitted contracts (`relay/storage/models.py`)

- `relay.stage_signal.v1` (`StageSignalPayload`) — validation only; the
  `Message` row is the durable record. Strict whole-output JSON,
  duplicate-key/non-finite/depth/size bounds, `extra="forbid"`.
- `relay.planner_decision.v1` (`PlannerDecisionPayload`) — `outcome:
  accept|reject`, `plan_effect: unchanged|supersede`; `supersede` requires
  non-empty `revised_plan`, `unchanged` forbids it, `reject` requires
  `unchanged`. `accepted_by` populates only on `accept`.
- `relay.plan_revision.v1` (`PlanRevisionPayload`) REPORT — links
  `supersedes_plan_artifact_id` → `plan_artifact_id` with
  `decision_id`/`signal_message_id`/`reply_message_id`/`author_run_id`
  provenance; minted atomically with the new PLAN + `PLAN_PRODUCED`
  evidence + the `Decision`.
- `relay.build.escalation.v1` (`BuildEscalationPayload`) REPORT — durable
  park observation; reasons `policy_refused|budget_exhausted|
  unresolved_role|self_send|delivery_failed|delivery_pending|
  turn_budget_exhausted`; deduped per signal message (or run+reason before
  a message exists).
- `relay.build.signal.invalid.v1` (`SignalInvalidPayload`) REPORT —
  intended-but-invalid signal diagnostic; the stage parks instead of
  falling through to diff/review parsing.

## Stage-boundary signal mechanism (`relay/core/stage_signals.py`)

`parse_stage_signal` mirrors `parse_review` strictness; the discriminator
is: output containing a `relay.stage_signal.*` marker that fails strict
parse/validation is ALWAYS a diagnostic + park — ordinary prose stays
pre-P6.4. `check_signal_legal` enforces the per-role kind/target matrix.
`compose_signal_message` translates to a `Message` (for
`challenge`/`proposal`, a `relay:`-delimited reply-contract appendix rides
inside the content — the D15 delivery envelope is frozen).
`canonical_replies_for` implements the strict pairing: `reply_to_id` +
`sender == parent.recipient` + `recipient == parent.sender` + non-blocking
+ the parent type's answer type. `resolve_open_signal` advances one open
signal one step — send if absent → `deliver_and_reply` → promote a
parseable planner decision — idempotent at every boundary; a failed
delivery retries once via a superseding send (at-most-once delivery makes
the original message undeliverable). `signal_appendix` advertises only
currently-deliverable signals; `exchange_appendix`/`notes_appendix` embed
the durable exchange history / role-addressed notes in stage prompts.

## Ledger changes (`relay/core/build_ledger.py`)

- Dispatch markers may carry `build_continuation:<message_id>` +
  `signal_reply:<reply_id>` (both-or-neither; forbidden on plan/fresh
  attempts). A repeated `build_attempt:N` or a repeated review-streak run
  REQUIRES both refs resolving to the immediately preceding run's latest
  blocking signal message and its canonical reply — anything less refuses
  `ledger_inconsistent`.
- Attempts are group-aware: `attempts` = last attempt number,
  `fix_runs_used = attempts - 1`; continuations never increment either.
  `pending_input` for a no-diff dispatch derives from the previous attempt
  group's last run.
- Signal state derivation: the latest no-diff impl run / latest review run
  is checked for a valid legal blocking signal — unanswered →
  `resolve_signal`, answered → `dispatch`/`review` continuation.
  Authored blocking messages without a valid signal, message/signal
  mismatch, or a DIFF minted by a signal run all refuse.
- Multiple `PLAN` artifacts resolve through the revision chain to the
  canonical tip; validation demands full decision/exchange provenance per
  hop. Orphan plans, cycles, double supersession → refuse.
- `in_flight_delivery_runs` scopes `--settle-interrupted` to RUNNING
  delivery runs serving OPEN signal messages — unrelated P4 deliveries are
  never touched.

## Orchestration (`relay/core/orchestrator.py`)

Signal detection runs before diff extraction / review parsing; a blocking
signal run mints nothing (never a DIFF, never a verdict). The driver gains
the `resolve_signal` action (escalate → `COMMUNICATION_BLOCKED` park,
answered → continuation dispatch) and same-attempt continuation dispatching
(marker refs + exchange-history prompt, no fix-budget consult).
`run_build`/`continue_build` accept `signals: SignalServices | None` —
`None` is byte-identical legacy behavior. `relay.build.loop.v1` is
unchanged; escalations/diagnostics are the observations.

## CLI

`relay build`/`relay continue` construct `SignalServices` from CURRENT
config (resolver, policy gate, bus, delivery — the `discussions.py`
wiring), so a corrected `relay.yaml` is what a continued build retries
against. `build_result` names the escalation/diagnostic artifact; the
records are ordinary REPORT artifacts in `relay inspect`.

## Non-goals

No mid-run cancellation; no convergence detection; no reviewer retry
redesign; no human-authored replies/@-addressing (P7+); no reviewer `note`;
no Room-scoped build messages; no `relay discuss` changes; no
message-level redelivery beyond the one superseding retry; no schema
migration.
